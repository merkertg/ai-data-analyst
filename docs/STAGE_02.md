## 3. Как запустить на Mac

### Шаг 1. Docker Desktop

PostgreSQL работает в контейнере Docker. Запусти Docker Desktop (иконка кита
в строке меню) и проверь:

```bash
docker info --format '{{.ServerVersion}}'
```

Ожидается номер версии, например `29.8.2`. Сообщение `failed to connect to
the docker API` значит, что Docker Desktop ещё не запущен.

### Шаг 2. Локальные настройки

```bash
cp .env.example .env
```

В `.env` лежат имя пользователя, пароль и порт базы, а также `DATABASE_URL`
для приложения. Пароль `local-development-only` годится только для локальной
разработки. Файл `.env` не попадает в Git.

### Шаг 3. Запустить PostgreSQL

```bash
docker compose up --detach --wait db
```

`--detach` возвращает терминал, `--wait` ждёт, пока healthcheck сообщит,
что база принимает соединения. Проверка:

```bash
docker compose ps
```

В столбце STATUS должно быть `Up ... (healthy)`, порт — `127.0.0.1:5436->5432/tcp`.

### Шаг 4. Создать таблицы миграцией

```bash
uv run alembic upgrade head
```

Фактический вывод:

```text
INFO  [alembic.runtime.migration] Running upgrade  -> 0001, Initial schema: customers, products, orders, items, refunds, inventory.
```

### Шаг 5. Загрузить учебный набор

```bash
uv run python -m app.db.sample
```

Вывод: `Учебный набор загружен: 2 клиента, 3 товара, 5 заказов, 2 возврата.`
Повторный запуск ничего не меняет: `В базе уже есть клиенты: учебный набор
не загружен.`

### Шаг 6. Проверить готовность API

```bash
uv run uvicorn app.main:app --reload
```

Во второй вкладке:

```bash
curl -i http://127.0.0.1:8000/ready
```

Ответ: `HTTP/1.1 200 OK` и `{"status":"ready","revision":"0001"}`.

### Шаг 7. Посмотреть на базу через psql

```bash
docker compose exec db psql -U analyst -d industrialflow
```

Внутри psql: `\dt` — список таблиц, `\d orders` — устройство таблицы,
`SELECT * FROM orders;` — строки, `\q` — выход.

### Шаг 8. Остановить

```bash
docker compose stop
```

Контейнер остановится, данные останутся в томе `ai-data-analyst_postgres_data`.
`docker compose down` удалит контейнер, но не том. **`docker compose down -v`
удалит и том — вместе со всеми данными.**

## 4. Реляционная модель: таблицы и связи

Реляционная база хранит данные в **таблицах**. Строка — одна запись (один
заказ), столбец — одно свойство (дата оплаты). У каждой строки есть
**первичный ключ** (`id`) — уникальный номер. Ссылка из одной таблицы на
строку другой — **внешний ключ**: `orders.customer_id` указывает на
`customers.id`.

```text
customers 1 ──< orders 1 ──< order_items >── 1 products 1 ──< inventory_snapshots
                                  │
                                  1
                                  └──< refunds
```

`1 ──<` читается «один ко многим»: у клиента много заказов, у заказа много
позиций, у позиции может быть несколько возвратов.

| Таблица | Основные поля | Что хранит |
| --- | --- | --- |
| `customers` | `name`, `region`, `industry` | Клиенты — промышленные предприятия |
| `products` | `sku` (уникальный артикул), `name`, `category`, `cost` | Каталог и себестоимость |
| `orders` | `customer_id`, `status`, `ordered_at`, `paid_at` | Заказы: когда оформлен, когда оплачен |
| `order_items` | `order_id`, `product_id`, `quantity`, `unit_price`, `discount` | Позиции: что, сколько, почём |
| `refunds` | `order_item_id`, `amount`, `processed_at` | Возвраты денег по позиции |
| `inventory_snapshots` | `product_id`, `snapshot_date`, `quantity` | Остаток товара на конец дня |

### Почему заказ разделён на две таблицы

Один заказ содержит несколько товаров. Если хранить всё в одной таблице,
пришлось бы либо повторять клиента и дату оплаты в каждой строке товара,
либо заводить столбцы «товар 1», «товар 2» … Оба варианта ломаются:
повторы расходятся при изменении, а число столбцов ограничено.

Решение — **нормализация**: каждое свойство хранится один раз там, где ему
место. Клиент и дата оплаты — в `orders`, товар, количество и цена —
в `order_items`. Регион хранится один раз в `customers`, а не в каждом заказе.

Цена продажи (`unit_price`) лежит в позиции, а не в товаре: цена меняется со
временем, а в истории продаж должна остаться та, по которой продали.

## 5. Правила целостности в самой базе

Правила записаны в PostgreSQL, а не только в Python. Некорректную строку
база отвергнет, даже если её вставит не наше приложение: скрипт генерации
данных, psql или будущий сервис.

| Вид | Что проверяет | Примеры в проекте |
| --- | --- | --- |
| `NOT NULL` | Значение обязательно | Клиент без региона не сохранится |
| `CHECK` | Условие для строки | `quantity > 0`, `discount >= 0 AND discount < 1`, `cost >= 0`, `amount > 0` |
| `CHECK` между столбцами | Согласованность полей | Оплаченный заказ обязан иметь `paid_at`, неоплаченный — не иметь; `paid_at >= ordered_at` |
| `UNIQUE` | Нет повторов | Артикул `sku`; один товар — одна строка заказа; один снимок остатка в день |
| `FOREIGN KEY` | Ссылка существует | Нельзя создать заказ несуществующего клиента |

### Что происходит при удалении

| Связь | Правило | Почему |
| --- | --- | --- |
| заказ → позиции | `ON DELETE CASCADE` | Позиции без заказа не имеют смысла: удаляются вместе с ним |
| клиент → заказы | `ON DELETE RESTRICT` | Клиента с историей продаж удалить нельзя |
| товар → позиции, остатки | `ON DELETE RESTRICT` | Проданный товар нельзя убрать из каталога |
| позиция → возвраты | `ON DELETE RESTRICT` | Проведённые деньги не исчезают; каскад удаления заказа тоже упирается в возврат |

Фактические ошибки PostgreSQL на базе разработки:

```text
ERROR:  new row for relation "order_items" violates check constraint "ck_order_items_quantity_positive"
ERROR:  update or delete on table "products" violates foreign key constraint
        "fk_inventory_snapshots_product_id_products" on table "inventory_snapshots"
```

### Имена ограничений

Имена задаёт соглашение в `app/db/base.py`:
`ck_<таблица>_<правило>`, `fk_<таблица>_<столбец>_<куда>`,
`uq_<таблица>_<столбцы>`, `ix_<таблица>_<столбцы>`. По имени из сообщения
об ошибке сразу видно, где и какое правило нарушено. Тесты проверяют именно
имя сработавшего ограничения.

### Чего база не проверяет

Некоторые правила охватывают несколько таблиц: сумма возвратов позиции
не больше её стоимости, возврат бывает только у оплаченного заказа. Обычный
`CHECK` видит одну строку, поэтому такие правила проверит контроль качества
данных на этапе 03.

## 6. Деньги и время

### Деньги — NUMERIC и Decimal

```python
>>> 0.1 + 0.2
0.30000000000000004
>>> from decimal import Decimal
>>> Decimal("0.1") + Decimal("0.2")
Decimal('0.3')
```

`float` хранит число в двоичном виде и не может точно представить 0.1.
Для денег это недопустимо: копейки накапливаются в ошибку отчёта. Поэтому:

- в PostgreSQL — `NUMERIC(12, 2)`: до 9 999 999 999.99 с точностью до копейки;
- скидка — `NUMERIC(5, 4)`: доля от 0 до 1, например `0.1250` = 12.5 %;
- в Python — `Decimal`. SQLAlchemy возвращает значения `NUMERIC` как `Decimal`.

Слишком большое значение база отвергнет ошибкой `numeric field overflow`,
а не исказит. Это проверяет тест `test_money_overflow_is_rejected`.

Сумма позиции = `ROUND(quantity * unit_price * (1 - discount), 2)` —
округление до копейки для каждой позиции, затем сложение.

### Время — timestamptz и московский месяц

`ordered_at`, `paid_at`, `processed_at` имеют тип `timestamp with time zone`.
PostgreSQL хранит **момент времени** (внутри — в UTC), а не «часы на стене».

Отчётный месяц компании считается по московскому времени. Заказ №5 учебного
набора оплачен 1 октября в 01:30 по Москве — это 30 сентября 22:30 по UTC.
Если сгруппировать по UTC, он попадёт в сентябрь. Поэтому запросы используют
`paid_at AT TIME ZONE 'Europe/Moscow'`. Тест `test_month_depends_on_time_zone`
показывает разницу: по UTC сентябрь дал бы 328 000.00 вместо 310 000.00.

## 7. SQLAlchemy 2: модели

SQLAlchemy — библиотека, которая описывает таблицы классами Python и
переводит операции с объектами в SQL. Фрагмент модели заказа:

```python
class Order(Base):
    __tablename__ = "orders"
    __table_args__ = (
        CheckConstraint(
            "status IN ('pending', 'paid', 'cancelled')", name="status_allowed"
        ),
        CheckConstraint(
            "(status = 'paid') = (paid_at IS NOT NULL)", name="paid_at_matches_status"
        ),
        Index(None, "paid_at"),
    )

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    customer_id: Mapped[int] = mapped_column(
        ForeignKey("customers.id", ondelete="RESTRICT")
    )
    paid_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))

    customer: Mapped[Customer] = relationship(back_populates="orders")
```

- `Mapped[int]` — тип для Python и mypy; `Mapped[datetime | None]` — столбец
  может быть пустым (`NULL`), `Mapped[int]` без `None` — `NOT NULL`.
- `mapped_column(...)` — тип в базе и ограничения столбца.
- `__table_args__` — ограничения и индексы всей таблицы.
- `relationship` — связь объектов в Python: `order.customer`,
  `customer.orders`. Это не столбец: столбец — `customer_id`.
- `Index(None, "paid_at")` — индекс для быстрого отбора по дате оплаты;
  имя `ix_orders_paid_at` даёт соглашение.

`OrderStatus` — перечисление Python со значениями `pending`, `paid`,
`cancelled`. Тест сверяет его с правилом `CHECK` в базе.

## 8. Engine, Session и транзакции

- **Engine** (`create_database_engine`) — пул соединений. Он создаётся
  лениво: импорт приложения и `/health` базу не трогают. `pool_pre_ping`
  проверяет соединение перед выдачей — после перезапуска PostgreSQL
  приложение само восстановилось (проверено ниже, в разделе 11).
  `connect_timeout=3` не даёт ждать недоступный сервер дольше трёх секунд.
- **Session** — рабочая область: объекты, которые добавили или изменили,
  уходят в базу при `flush()` и фиксируются при `commit()`.
- **Транзакция** — группа изменений «всё или ничего». Если на середине
  случилась ошибка, `rollback()` отменяет всё, что было сделано в ней.

```python
with Session(get_engine()) as session:
    add_sample_data(session)  # flush: строки отправлены, но не зафиксированы
    session.commit()  # фиксация: теперь их видят другие соединения
```

`get_session()` в `app/db/session.py` — заготовка для FastAPI (этап 06):
выдаёт сессию, при ошибке откатывает её и всегда возвращает соединение
в пул. Скрытого `commit` после запроса нет — код, который пишет данные,
фиксирует их сам.

## 9. Alembic: миграции схемы

Схема базы меняется вместе с кодом: новые таблицы, столбцы, правила.
**Миграция** — файл с шагом изменения схемы (`upgrade`) и его отменой
(`downgrade`). Alembic хранит номер применённой версии в таблице
`alembic_version` и знает, какие шаги ещё не выполнены.

Почему не `Base.metadata.create_all()`: он умеет только создавать
отсутствующие таблицы и не меняет существующие. Миграции дают историю,
откат и одинаковую схему у всех.

| Файл | Роль |
| --- | --- |
| `alembic.ini` | Где лежат миграции, формат имён файлов, журналы. Адреса базы нет |
| `migrations/env.py` | Берёт адрес из `DATABASE_URL` (или из теста) и метаданные моделей |
| `migrations/versions/0001_initial_schema.py` | `upgrade()` создаёт 6 таблиц, `downgrade()` удаляет их |

Как создана первая миграция:

```bash
uv run alembic revision --autogenerate --rev-id 0001 -m "Initial schema"
```

Alembic сравнил модели с пустой базой и записал команды `create_table`,
`create_index`. Автогенерация — черновик: файл обязательно читают глазами.
Здесь проверено, что таблицы создаются в порядке зависимостей и удаляются
в обратном.

| Команда | Что делает |
| --- | --- |
| `uv run alembic upgrade head` | Применить все неприменённые миграции |
| `uv run alembic downgrade -1` | Откатить одну миграцию |
| `uv run alembic downgrade base` | Откатить всё — **с удалением данных** |
| `uv run alembic current` | Какая версия в базе: `0001 (head)` |
| `uv run alembic history` | Список миграций: `<base> -> 0001 (head)` |
| `uv run alembic check` | Есть ли изменения моделей без миграции: `No new upgrade operations detected.` |
| `uv run alembic upgrade head --sql` | Показать SQL, не выполняя его |

Правило: **применённую миграцию не редактируют**. Любое изменение схемы —
новая миграция `0002`, `0003` … Иначе у разных людей окажутся разные базы
с одинаковым номером версии.

## 10. Docker Compose и PostgreSQL

`compose.yaml` описывает два сервиса на одном образе
`postgres:17@sha256:2d2b…` (закреплён по digest, как в первом проекте):

| | `db` | `db-test` |
| --- | --- | --- |
| Назначение | Разработка | Интеграционные тесты |
| Запуск | `docker compose up --detach --wait db` | `docker compose --profile test up --detach --wait db-test` |
| Порт | `127.0.0.1:5436` | `127.0.0.1:5437` |
| База | `industrialflow` | `industrialflow_test` |
| Данные | Том `postgres_data` — переживают пересоздание | `tmpfs` в памяти — исчезают при остановке |

- Порт опубликован только на `127.0.0.1`: база недоступна из локальной сети.
- 5436/5437, а не стандартный 5432: не конфликтуем с другими PostgreSQL на Mac
  (первый проект использует 5433/5434).
- `healthcheck` с `pg_isready` — Compose знает, когда база действительно готова.
- Пароль берётся из `.env`; без него `docker compose up` остановится с подсказкой.

Проверено: после `docker compose down` и нового `up` контейнер сменился,
а в базе остались те же 5 заказов и версия схемы `0001`.

## 11. Готовность: /health и /ready

| | `/health` | `/ready` |
| --- | --- | --- |
| Вопрос | Процесс жив? | Можно принимать запросы? |
| Обращается к базе | Нет | Да: соединение + версия схемы |
| Без базы | 200 | 503 |

`/ready` открывает соединение, читает `alembic_version` и сравнивает версию
с последней миграцией в коде (`expected_revision()`). Пустая, недоступная
или отставшая база — 503 с одинаковым текстом `Database is not ready`:
адрес и ошибки драйвера наружу не выходят.

Фактическая проверка на настоящем сервере:

```text
база работает:      HTTP/1.1 200 OK                   {"status":"ready","revision":"0001"}
docker compose stop db:  HTTP/1.1 503 Service Unavailable  {"detail":"Database is not ready"}
docker compose start db: HTTP/1.1 200 OK                   {"status":"ready","revision":"0001"}
```

Третий ответ показывает работу `pool_pre_ping`: пул выбросил разорванные
соединения и открыл новые без перезапуска приложения.

## 12. SQL-запросы вручную

Учебный набор (`app/db/sample.py`) специально маленький — все ответы
посчитаны на бумаге:

| Заказ | Клиент | Статус | Состав | Сумма |
| --- | --- | --- | --- | --- |
| №1 | ТехМонтаж-Север | оплачен 5 сен | 2 насоса × 100 000 − 10 %, 5 датчиков × 2 000 | 190 000.00 |
| №2 | Южный химкомбинат | оплачен 20 сен | 1 насос × 120 000 | 120 000.00 |
| №3 | Южный химкомбинат | отменён | 10 кранов × 4 500 | — |
| №4 | ТехМонтаж-Север | не оплачен | 3 датчика × 2 000 | — |
| №5 | ТехМонтаж-Север | оплачен 1 окт 01:30 МСК | 4 крана × 4 500 | 18 000.00 |

Возвраты по датчикам заказа №1: 1 000.00 (10 сентября) и 500.00 (2 октября).

Запуск любого файла:

```bash
docker compose exec -T db psql -U analyst -d industrialflow < sql/02_net_revenue_by_month.sql
```

### 01 — сумма оплаченных заказов: JOIN и GROUP BY

`JOIN` соединяет заказ с клиентом и позициями, `WHERE status = 'paid'`
оставляет оплаченные, `GROUP BY` сворачивает позиции в одну строку на заказ.

```text
 order_id |        customer        |        paid_at         | items | order_total
        1 | ООО «ТехМонтаж-Север»  | 2026-09-05 09:00:00+00 |     2 |   190000.00
        2 | АО «Южный химкомбинат» | 2026-09-20 06:30:00+00 |     1 |   120000.00
        5 | ООО «ТехМонтаж-Север»  | 2026-09-30 22:30:00+00 |     1 |    18000.00
```

psql показывает время в UTC (`+00`): 09:00 UTC = 12:00 по Москве.

### 02 — чистая выручка по месяцам: CTE и FULL OUTER JOIN

`WITH sales AS (...)` и `refunded AS (...)` — именованные подзапросы (CTE):
продажи по месяцу оплаты и возвраты по месяцу проведения считаются
отдельно. `FULL OUTER JOIN` сохраняет месяц, где были только продажи или
только возвраты.

```text
   month    | paid_sales | refunds | net_revenue
 2026-09-01 |  310000.00 | 1000.00 |   309000.00
 2026-10-01 |   18000.00 |  500.00 |    17500.00
```

Это правило из плана курса: *Net Revenue = Paid Sales − Processed Refunds*,
возврат уменьшает выручку месяца, в котором он проведён.

### 03 — продажи по категориям: оконная функция

`SUM(...) OVER ()` — оконная функция: она видит сумму по всем строкам
результата, не схлопывая их. Так считается доля каждой категории.

```text
     category      | paid_sales | share_percent
 Насосы            |  300000.00 |          91.5
 Запорная арматура |   18000.00 |           5.5
 Датчики           |   10000.00 |           3.0
```

### 04 — ловушка двойного подсчёта

Если присоединить `refunds` к позициям и потом сложить суммы позиций,
позиция с двумя возвратами попадёт в сумму дважды:

```text
 naive_sales | correct_sales | refunds
   338000.00 |     328000.00 | 1500.00
```

Лишние 10 000.00 — это повторно посчитанная позиция «5 датчиков». Правило:
сначала свести каждую таблицу «многих» к одной строке на ключ (или посчитать
суммы отдельно, как в запросе 02), и только потом соединять.

| Группа | Сколько | Нужна база | Что проверяет |
| --- | --- | --- | --- |
| Unit | 26 | Нет | Настройки и адрес базы, `/health`, `/ready` без базы, ленивый пул, структура моделей |
| Интеграционные | 34 | Да, `*_test` | Миграции вверх и вниз, `alembic check`, `/ready` на настоящей базе, 20 нарушений правил, каскад удаления, точность денег, часовой пояс, 4 SQL-запроса |

### Как запустить

```bash
docker compose --profile test up --detach --wait db-test
TEST_DATABASE_URL='postgresql+psycopg://analyst:analyst_test@127.0.0.1:5437/industrialflow_test' uv run pytest
```

Результат: `60 passed`. Без `TEST_DATABASE_URL` интеграционные тесты
пропускаются: `26 passed, 34 skipped`. В GitHub Actions (`CI=true`)
отсутствие адреса — ошибка, а не пропуск.

### Почему отдельная база и суффикс _test

Интеграционные тесты удаляют и создают схему заново. Адрес берётся только
из `TEST_DATABASE_URL` — не из `DATABASE_URL` и не из `.env`, где может быть
база разработки. Если имя базы не заканчивается на `_test`, тесты
отказываются работать.

### Как тесты не мешают друг другу

- `migrated_engine` — один раз за прогон: `downgrade base` → `upgrade head`.
  Схема создаётся только миграциями, как у пользователя.
- `db_session` — каждый тест работает внутри транзакции, которая
  откатывается в конце. Данные одного теста не видны другому, чистить
  таблицы не нужно.

### Пример теста ограничения

```python
@pytest.mark.parametrize("case", CASES, ids=list(CASES))
def test_invalid_row_is_rejected(db_session: Session, case: str) -> None:
    build, constraint = CASES[case]
    db_session.add(build(base_rows(db_session)))

    with pytest.raises(IntegrityError) as error:
        db_session.flush()

    assert violated_constraint(error.value) == constraint
```

Тест не просто ждёт ошибку — он проверяет **имя** сработавшего ограничения
из диагностики PostgreSQL. Так ошибка «не того» правила не пройдёт незамеченной.

## 16. Проверь себя

1. Почему заказ хранится в двух таблицах, `orders` и `order_items`?
2. Чем `ON DELETE CASCADE` отличается от `ON DELETE RESTRICT` и где в проекте каждое?
3. Почему деньги — `NUMERIC` и `Decimal`, а не `float`?
4. Зачем `AT TIME ZONE 'Europe/Moscow'` в запросах по месяцам?
5. Чем миграция Alembic лучше `create_all()`? Почему применённую миграцию не редактируют?
6. Почему JOIN позиций с возвратами завышает продажи и как этого избежать?
7. Чем `/ready` отличается от `/health`?
8. Зачем интеграционным тестам база с суффиксом `_test`?

<details>
<summary>Ответы</summary>

1. Один заказ — много товаров. Нормализация: свойства заказа хранятся один
   раз в `orders`, свойства каждого товара в заказе — в `order_items`.
2. CASCADE удаляет зависимые строки вместе с родителем (позиции с заказом),
   RESTRICT запрещает удалить родителя, пока есть ссылки (клиент с заказами,
   проданный товар, позиция с возвратом).
3. `float` двоичный и не хранит 0.1 точно: копейки накапливаются в ошибку.
   `NUMERIC`/`Decimal` хранят десятичные числа точно.
4. `paid_at` — момент в UTC. Отчётный месяц компании — московский: заказ,
   оплаченный 1 октября в 01:30 МСК, по UTC попал бы в сентябрь.
5. Миграции дают историю, откат и одинаковую схему у всех; `create_all`
   умеет только создать отсутствующие таблицы. Изменённая применённая
   миграция даст разные базы с одинаковым номером версии.
6. Позиция повторяется в результате JOIN на каждый свой возврат. Нужно
   сначала свести таблицы к одной строке на ключ или считать суммы отдельно.
7. `/health` — процесс жив, база не нужна. `/ready` — база доступна и схема
   совпадает с кодом; иначе 503.
8. Тесты сбрасывают схему. Суффикс защищает базу разработки от случайного
   удаления данных.

</details>
