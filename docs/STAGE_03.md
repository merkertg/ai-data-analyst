# Этап 03. Воспроизводимые данные и проверка качества

На третьем этапе у IndustrialFlow появляется большой вымышленный набор
данных для будущей аналитики. Генератор создаёт заказы, товары, клиентов,
возвраты и ежедневные остатки. Загрузчик переносит их в PostgreSQL одной
транзакцией, а отдельная команда проверяет правила, затрагивающие несколько
строк и таблиц. LLM на этом этапе ещё нет: данные и все финансовые величины
вычисляет Python-код.

Короткая английская инструкция: [Demo data](instructions/demo-data.md).
Архитектурное решение: [ADR 0003](adr/0003-reproducible-demo-data-and-safe-loading.md).
Наглядные версии: [PDF на русском](guide/ai-data-analyst-guide.pdf) и
[PDF на английском](guide/ai-data-analyst-guide-en.pdf).
Фактические проверки и их ограничения: [VERIFICATION.md](VERIFICATION.md).

## 1. Что добавлено

| Часть | Команда | Назначение |
| --- | --- | --- |
| Генератор | `python -m app.data.generate` | Создать воспроизводимый набор CSV без подключения к базе |
| Загрузчик | `python -m app.data.load` | Проверить файлы и загрузить их в пустые таблицы одной транзакцией |
| Проверка качества | `python -m app.data.quality` | Прочитать базу и проверить межтабличные правила |
| Манифест | `manifest.json` | Версия формата, seed, число строк и контрольные суммы |
| Ответы для оценки | `ground_truth.json` | Исходные и изменённые показатели пяти сценариев |

Значения по умолчанию: 640 клиентов, 64 товара, восемь регионов и 20 000
заказов за январь–сентябрь 2026 года. Компания, клиенты и операции вымышлены.
Месяцы определяются в часовом поясе `Europe/Moscow`, как в предыдущем этапе.

```text
параметры + seed
      │
      ▼
 app.data.generate ──► 6 CSV + manifest.json + ground_truth.json
                              │                      │
                              ▼                      └──► только оценка
                         app.data.load                    будущей аналитики
                              │
                              ▼
                  PostgreSQL: 6 пустых таблиц
                              │
                              ▼
                    app.data.quality
                    чтение без изменений
```

Следующий этап 04 создаёт аналитические функции. Автоматическое обнаружение
аномалий, REST API метрик, LLM-агент и интерфейс появятся позднее.

## 2. Что значит воспроизводимость

Обычный генератор случайных чисел выдаёт разные данные при каждом запуске.
Для учебного проекта это неудобно: вчера в сентябре было одно падение продаж,
сегодня другое, и тесту не с чем сравнить ответ.

Здесь `seed` задаёт начальное состояние отдельного `random.Random`.
Одинаковые параметры дают одинаковые байты файлов. Значение `42` не обладает
особым деловым смыслом: это выбранная точка отсчёта. Другой `seed` создаёт
другой набор, а не «более правильные» данные.

Генератор использует стандартную библиотеку Python. NumPy и Faker для этого
этапа не нужны. Финансовые вычисления выполняются через `Decimal`, числа в
CSV записываются десятичным текстом, а в PostgreSQL попадают в `NUMERIC`.
Например, сумма позиции считается так:

```text
quantity × unit_price × (1 − discount), округление до 0.01
```

Важно округлять именно сумму позиции, а затем складывать позиции. Это
сохраняет правила метрик, зафиксированные в [APPROACH.md](APPROACH.md).

## 3. Как создать набор

Все команды выполняются из корня проекта, где лежит `pyproject.toml`.

```bash
uv sync --locked
uv run python -m app.data.generate --output data/demo --seed 42 --orders 20000
```

База данных и Docker для генерации не нужны. Каталог `data/demo` должен быть
новым или пустым: существующие файлы генератор не перезаписывает. Для второго
набора укажи другой путь, например `data/demo-repeat`. Число заказов можно
выбрать от 1 000 до 100 000; количество клиентов и товаров фиксировано.
Посмотреть параметры:

```bash
uv run python -m app.data.generate --help
```

В каталоге появятся:

```text
data/demo/
├── customers.csv
├── products.csv
├── orders.csv
├── order_items.csv
├── refunds.csv
├── inventory_snapshots.csv
├── manifest.json
└── ground_truth.json
```

CSV соответствуют шести таблицам из этапа 02. Заказ и его позиции остаются
разными сущностями: число строк в `order_items.csv` не обязано совпадать с
числом заказов. Снимки остатков показывают состояние товара на конкретную
дату. Сгенерированный каталог не включается в Git; исходник генератора,
инструкции и тесты позволяют создать его повторно.

Для проверки воспроизводимости создай второй набор с теми же параметрами:

```bash
uv run python -m app.data.generate --output data/demo-repeat --seed 42 --orders 20000
diff -r data/demo data/demo-repeat
```

Если `diff` не выводит различий и завершился с кодом `0`, файлы совпадают.
Проверка относится к одинаковым параметрам и версии генератора.

## 4. Зачем нужен manifest.json

Манифест описывает версию формата, seed, число строк таблиц и контрольные
суммы CSV. Загрузчик проверяет шесть CSV и манифест до импорта. Файл
`ground_truth.json` он не читает: ответ для оценки отделён от загрузки.

Контрольная сумма меняется при изменении байтов файла. Поэтому случайно
отредактированный CSV, повреждённая копия или неполный набор обнаруживаются
до загрузки. Контрольная сумма не подтверждает автора: человек, способный
изменить и CSV, и манифест, может пересчитать её. Для вымышленного локального
набора это проверка целостности, а не механизм подписи.

Не исправляй сгенерированный набор вручную для получения нужного результата
теста. Исправь правило в генераторе, создай новый набор в новом каталоге и
проверь его. `ground_truth.json` остаётся служебным ответом для оценки.

## 5. Как загрузить данные в PostgreSQL

Подготовь `.env`, запусти базу и примени миграции, как в этапе 02:

```bash
docker compose up --detach --wait db
uv run alembic upgrade head
uv run python -m app.data.load --input data/demo
```

Адрес базы загрузчик берёт из обычных настроек `DATABASE_URL`. Перед загрузкой
он требует, чтобы **все шесть предметных таблиц были пустыми**. Таблица версии
Alembic при этом должна существовать после миграции. Если ранее загружен
маленький учебный набор `app.db.sample`, эта база уже не пуста. Для большого
набора выбери отдельную пустую базу с применёнными миграциями.

У загрузчика нет параметра сброса или перезаписи. Повторный запуск на уже
загруженных данных завершается отказом. Это защищает существующие данные и
исключает случайное удвоение продаж.

Импорт выполняется в одной транзакции. Сначала создаются сущности, на которые
ссылаются остальные: клиенты и товары, затем заказы, позиции, возвраты и
остатки. Пока транзакция не завершена, набор не считается загруженным. Если
возникает ошибка, изменения откатываются целиком. Нельзя получить
зафиксированных клиентов без соответствующих заказов из неудачного импорта.

## 6. Аномалия бизнеса и ошибка данных

Эти понятия отвечают на разные вопросы.

| Пример | Что это означает |
| --- | --- |
| Количество позиции равно нулю | Нарушено правило строки; PostgreSQL отклоняет её |
| Два возврата вместе больше суммы позиции | Межтабличная ошибка; её выявляет проверка качества |
| Заказ оплачен, но возврат проведён раньше оплаты | Противоречие дат; его выявляет проверка качества |
| Продажи насосов резко сократились | Возможное необычное событие бизнеса; строка может быть полностью корректной |
| Один клиент купил 500 датчиков | Большой заказ для исследования; положительное количество допустимо |

Генератор внедряет пять **допустимых деловых сценариев**. Они должны пройти
проверку целостности. Их необычность будет исследовать аналитика, а позднее
алгоритмы обнаружения аномалий.

## 7. Пять сценариев A01–A05

| ID | Изменение | Какой вопрос можно исследовать |
| --- | --- | --- |
| A01 | В сентябрьских оплаченных позициях насосов количество уменьшается до 40% исходного, с округлением вниз и минимумом 1 | Как насосы повлияли на изменение продаж? |
| A02 | В августе у оплаченных позиций арматуры в южном регионе скидка 35% | Как скидка изменила продажи и средний чек? |
| A03 | В июле добавляется возврат 30% округлённой суммы каждой оплаченной позиции компрессоров | Как возвраты повлияли на чистую выручку? |
| A04 | У товара 1, насоса, остаток равен нулю 10–19 сентября | Какие даты отсутствия товара совпадают со снижением продаж? |
| A05 | У одной оплаченной июньской позиции датчиков количество равно 500 | Как крупная позиция влияет на распределение размеров заказов? |

Возврат A03 добавляется к исходным возвратам, если они уже были: это не
обещание, что общая доля возвратов всех компрессоров равна ровно 30%.

У A01 уменьшение количества не означает, что итоговая выручка всей категории
обязательно упала ровно на 60%: результат зависит от других позиций, цен,
скидок, статусов и возвратов. Снижение до 40% относится к преобразованию
выбранных количеств относительно их исходных значений.

A01 и A04 существуют в одном вымышленном наборе. Это позволяет сформулировать
гипотезу об остатках, но не доказывает, что отсутствие одного товара вызвало
снижение продаж всех насосов. В отчёте нужно разделять вычисленное наблюдение
и предполагаемое объяснение.

## 8. Что хранит ground_truth.json

Файл содержит исходные и наблюдаемые значения, а также сведения о внедрённых
сценариях. Они вычисляются тем же детерминированным кодом и позволяют
проверить, обнаружила ли будущая аналитика нужное изменение.

Это ответ для оценки, а не источник деловых фактов для агента. Будущий агент
должен запрашивать таблицы через аналитические инструменты и сам получать
показатели. Если передать ему `ground_truth.json`, проверка перестанет
показывать умение исследовать данные: ответ уже будет раскрыт.

## 9. Как проверить качество

```bash
uv run python -m app.data.quality
```

Команда читает базу, выбранную через `DATABASE_URL`, и не меняет её. Код
завершения `0` означает, что перечисленные проверки прошли; `1` — найдены
нарушения.

Проверяются четыре правила:

1. Каждый заказ должен иметь хотя бы одну позицию.
2. Сумма всех возвратов одной позиции не должна превышать её округлённую сумму
   после скидки: `ROUND(quantity * unit_price * (1 - discount), 2)`.
3. Возвраты допустимы только для оплаченных заказов.
4. Дата возврата не должна предшествовать дате оплаты.

Почему нужен итог по всем возвратам? Позиция стоит 100 рублей. Два возврата
по 60 рублей каждый по отдельности положительны и меньше 100, но вместе
составляют 120. Простое ограничение на одну строку не видит эту ошибку.

Совсем пустая база без заказов не нарушает правило «каждый заказ имеет
позиции»: в ней нет ни одного заказа без позиций. Проверка качества
не подтверждает, что демонстрационный набор уже загружен; для этого нужно
сверить число строк с манифестом.

PostgreSQL уже проверяет внешние ключи, уникальность, положительность
количеств и остальные правила этапа 02. Новая команда дополняет их. Успешный
результат не гарантирует отсутствие всех возможных ошибок и не означает,
что в бизнесе нет аномалий. Она также не исправляет найденные нарушения.

## 10. Проверки реализации

Общие команды приведены в [Testing](instructions/testing.md). Модульные
тесты проверяют воспроизводимость и договорённости файлового формата.
Интеграционные проверки используют настоящую PostgreSQL: загрузку, полный
откат при ошибке, отказ от повторного импорта и нарушения качества данных.

Интеграционные тесты получают адрес только из `TEST_DATABASE_URL`, а имя базы
должно заканчиваться на `_test`. Базу разработки из `.env` они не используют.
Проверка `app.data.quality` в обычном запуске читает `DATABASE_URL`; это
отдельная команда, не настройка тестов.

Точное число тестов и фактические результаты записаны в
[VERIFICATION.md](VERIFICATION.md). Локально прошедший тест не подтверждает
успех удалённого GitHub Actions: для него нужен отдельно проверенный запуск.

## 11. Частые затруднения

| Симптом | Причина и действие |
| --- | --- |
| Генератор отказывается писать в `data/demo` | Каталог уже содержит файлы; выбери новый каталог |
| Загрузчик обнаружил существующие строки | В базе уже есть учебный или большой набор; используй отдельную пустую базу после миграций |
| Проверка набора не прошла | Сверь входной каталог и комплект файлов; создай набор заново в другом каталоге |
| Проверка качества нашла заказ без позиций | Есть строка заказа без товаров; проверь целостность импорта и связанные позиции |
| Проверка качества нашла возврат выше суммы | Сравни сумму всех возвратов с округлённой суммой позиции; команда сама ничего не исправляет |
| Интеграционные тесты пропущены | Локально не задан `TEST_DATABASE_URL`; настрой отдельную базу `_test` |

## 12. Проверь себя

1. Почему одинаковый `seed` недостаточен, если изменились параметры генерации?
2. Зачем хранить сумму денег строкой в CSV и `Decimal` в Python?
3. Почему загрузчик проверяет пустоту всех шести таблиц?
4. Что останется в базе после ошибки в середине одной транзакции импорта?
5. Почему два корректных по отдельности возврата могут нарушить общее правило?
6. Почему нулевой остаток допустим, а нулевое количество проданной позиции — нет?
7. Чем `ground_truth.json` отличается от источника данных для агента?
8. Почему совпадения A01 и A04 недостаточно для вывода о причине падения продаж?

Практика: создай два набора с одинаковыми параметрами в разных каталогах и
сравни их. Затем создай третий с другим `seed` и объясни, какие свойства
должны сохраниться (формат, правила целостности, смысл сценариев), а какие
могут измениться (конкретные заказы и вычисленные величины).
