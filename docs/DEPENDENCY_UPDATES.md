# Обновление Python-зависимостей

Как в проекте выбираются версии пакетов, как проверяются уязвимости и как
обновить зависимости. Решения — в [ADR 0001](adr/0001-application-layout-and-tooling.md)
и [ADR 0010](adr/0010-docker-packaging-and-delivery.md).

## Что зафиксировано

| Файл | Что хранит |
| --- | --- |
| `pyproject.toml` | Нижние границы прямых зависимостей и дату `[tool.uv] exclude-newer` |
| `uv.lock` | Точные версии и хэши всех 81 пакетов (с dev-группой) |
| `scripts/audit-exceptions.json` | Временно принятые уязвимости: причина и срок |

`uv sync --locked` и сборка образа ставят ровно то, что в `uv.lock`.
Если `pyproject.toml` и lock расходятся, CI останавливается на первом шаге.

## Политика 14 дней

`exclude-newer = "2026-10-06T00:00:00Z"`: uv не видит выпуски PyPI новее этой
даты. Причина — атаки на цепочку поставок: взломанный выпуск обычно
обнаруживают и удаляют в первые дни. При обновлении дату сдвигают не ближе
чем на 14 дней к текущему дню.

## Аудит уязвимостей

```bash
uv run python scripts/audit_dependencies.py
```

Скрипт экспортирует runtime-зависимости (`uv export --no-dev`, с хэшами),
запускает pip-audit 2.10.1 и сравнивает находки со списком исключений:

Перед запуском pip-audit скрипт удаляет предыдущий `reports/pip-audit.json`.
Для проверки нужен новый JSON с корректной структурой зависимостей и находок;
код завершения должен соответствовать содержимому отчёта. Отсутствующий или
повреждённый отчёт, ошибка запуска и несовпадение кода с находками останавливают
аудит. Например, код завершения «найдены уязвимости» вместе с пустым списком
находок считается ошибкой. Старый успешный отчёт не может подменить результат
неудачного запуска.

| Ситуация | Результат |
| --- | --- |
| Находок нет | Успех |
| Находка есть в исключениях, срок не истёк | Успех, находка учтена как принятая |
| Находки нет в исключениях | **Ошибка** |
| Срок исключения истёк | **Ошибка** |
| Исключение для уже исправленной находки | **Ошибка**: удалить запись |
| Новый отчёт отсутствует, повреждён или не соответствует коду завершения | **Ошибка** |
| pip-audit завершился с операционной ошибкой | **Ошибка** |

Отчёт пишется в `reports/pip-audit.json`; в CI он сохраняется артефактом
`dependency-audit` на 7 дней. Аудит запускается на каждый push и pull request.

Проверку обработки отчётов можно повторить без сети: тесты подменяют внешние
команды и создают временные JSON-файлы.

```bash
uv run pytest -q tests/test_audit_dependencies.py
```

## Текущие исключения (22 октября 2026 года)

| Пакет | Уязвимостей | Исправление | Можно взять по политике | Срок исключения |
| --- | --- | --- | --- | --- |
| `pillow 12.3.0` | 24 | `13.0.0` (16.10) + Streamlit `1.66` (14.10) | 30 октября | 6 ноября |
| `certifi 2026.7.22` | 1 | `2026.10.19` (20.10) | 3 ноября | 6 ноября |

Почему риск допустим: код проекта не декодирует, не загружает и не сохраняет
изображения, Pillow приходит только через Streamlit. Единственный исходящий
HTTPS-запрос — к OpenAI с фиксированным адресом; проблема certifi — один
корневой сертификат, которому больше нельзя доверять.

## Как обновить (план на 3–6 ноября)

```bash
# 1. Сдвинуть дату не ближе 14 дней к сегодняшней.
#    pyproject.toml: exclude-newer = "2026-10-21T00:00:00Z"
# 2. Поднять нужные пакеты и пересобрать lock.
uv add "streamlit>=1.66,<2"
uv lock --upgrade-package pillow --upgrade-package certifi
# 3. Убедиться, что уязвимостей больше нет, и удалить исключения.
uv run python scripts/audit_dependencies.py
# 4. Полная проверка, как в CI.
uv run ruff check . && uv run mypy app ui tests migrations
TEST_DATABASE_URL=… uv run pytest --cov
docker compose up --build --detach --wait
```

Аудит после обновления сам напомнит удалить исключения: запись для
исправленной уязвимости становится «stale» и роняет проверку. Изменения
lock, `pyproject.toml` и `audit-exceptions.json` фиксируются одним коммитом.

## Обновление в обычном порядке

1. Сдвинуть `exclude-newer` (не ближе 14 дней).
2. `uv lock --upgrade` — обновить всё в пределах границ `pyproject.toml`,
   или `--upgrade-package <имя>` — один пакет.
3. Прочитать diff `uv.lock`: какие версии изменились.
4. Аудит, Ruff, mypy, тесты с покрытием, стенд Docker.
5. Отдельный коммит «Update dependencies to …».

В первом проекте те же шаги выполняет еженедельный workflow, который
открывает pull request. Здесь обновление ручное: проект завершён,
и автоматизация — возможное развитие.
