# Обновление Python-зависимостей

Как в проекте выбираются версии пакетов, как проверяются уязвимости и как
обновить зависимости. Решения — в [ADR 0001](adr/0001-application-layout-and-tooling.md)
и [ADR 0010](adr/0010-docker-packaging-and-delivery.md).

## Что зафиксировано

| Файл | Что хранит |
| --- | --- |
| `pyproject.toml` | Нижние границы прямых зависимостей, ограничения исправленных транзитивных пакетов и даты допуска выпусков |
| `uv.lock` | Точные версии и хэши runtime- и dev-зависимостей |
| `scripts/audit-exceptions.json` | Временно принятые уязвимости: причина и срок |

`uv sync --locked` и сборка образа ставят ровно то, что в `uv.lock`.
Если `pyproject.toml` и lock расходятся, CI останавливается на первом шаге.

## Политика 14 дней

Общая граница на 23 октября — `exclude-newer = "2026-10-09T00:00:00Z"`:
для обычных обновлений uv не видит выпуски PyPI новее этой даты. Дату
сдвигают не ближе чем на 14 дней к текущему дню, чтобы уменьшить риск
установки скомпрометированного свежего выпуска.

Исправление уже известных уязвимостей может требовать более свежего пакета.
В таком случае точечная дата в `[tool.uv.exclude-newer-package]` допускает
нужный выпуск только для названного пакета; остальные зависимости остаются
под общей границей. Это исключение из правила возраста выпуска, а не
принятие уязвимости и не отключение аудита.

### Обновление безопасности 23 октября 2026 года

После сообщения CI о 37 находках (25 ранее принятых и 12 новых) выбрано
обновление зависимостей вместо расширения `audit-exceptions.json`:

| Пакет | Минимальная версия | Дата допуска выпуска | Причина |
| --- | --- | --- | --- |
| `streamlit` | `1.66.1` | `2026-10-22T00:00:00Z` | Совместимость с Pillow 13 |
| `pillow` | `13.0.0` | `2026-10-17T00:00:00Z` | Исправления уязвимостей Pillow |
| `certifi` | `2026.10.19` | `2026-10-21T00:00:00Z` | Обновлённое хранилище доверенных сертификатов |
| `opentelemetry-api` | `1.45.1` | Общая граница `2026-10-09T00:00:00Z` | Исправление новой находки аудита |

Исходный совет «Streamlit 1.66 достаточно для Pillow 13» был неверен:
**Streamlit 1.66.0 всё ещё требует `pillow<13`; нужна версия 1.66.1**.
Прямая нижняя граница Streamlit и ограничения транзитивных пакетов защищают
последующие разрешения зависимостей от возврата к уязвимым версиям.
Даты допуска не плавающие: новое исключение или его расширение требует
отдельного разбора конкретного обновления безопасности.

## Аудит уязвимостей

```bash
uv run python scripts/audit_dependencies.py
```

Скрипт экспортирует runtime-зависимости (`uv export --no-dev`, с хэшами),
запускает pip-audit 2.10.1 и сравнивает находки со списком исключений:

Перед запуском pip-audit скрипт удаляет предыдущий `reports/pip-audit.json`.
Для проверки нужен новый JSON с корректной структурой зависимостей и находок;
код завершения должен соответствовать содержимому отчёта. Отсутствующий или
повреждённый отчёт, ошибка запуска и несовпадение кода с находками останавливают
аудит. Например, код завершения «найдены уязвимости» вместе с пустым списком
находок считается ошибкой. Старый успешный отчёт не может подменить результат
неудачного запуска.

| Ситуация | Результат |
| --- | --- |
| Находок нет | Успех |
| Находка есть в исключениях, срок не истёк | Успех, находка учтена как принятая |
| Находки нет в исключениях | **Ошибка** |
| Срок исключения истёк | **Ошибка** |
| Исключение для уже исправленной находки | **Ошибка**: удалить запись |
| Новый отчёт отсутствует, повреждён или не соответствует коду завершения | **Ошибка** |
| pip-audit завершился с операционной ошибкой | **Ошибка** |

Отчёт пишется в `reports/pip-audit.json`; в CI он сохраняется артефактом
`dependency-audit` на 7 дней. Аудит запускается на каждый push и pull request.

Проверку обработки отчётов можно повторить без сети: тесты подменяют внешние
команды и создают временные JSON-файлы.

```bash
uv run pytest -q tests/test_audit_dependencies.py
```

## История: временные исключения 22 октября 2026 года

| Пакет | Уязвимостей | Исправление | Можно взять по политике | Срок исключения |
| --- | --- | --- | --- | --- |
| `pillow 12.3.0` | 24 | `13.0.0` (16.10) + Streamlit `1.66.1`; прежний совет о `1.66` исправлен | Старый план: 30 октября | 6 ноября |
| `certifi 2026.7.22` | 1 | `2026.10.19` (20.10) | 3 ноября | 6 ноября |

Тогда для Pillow ссылались на отсутствие декодирования изображений в коде
проекта. Прежний довод о фиксированном OpenAI-хосте для certifi был
недостаточен: скомпрометированный промежуточный сертификат emSign мог
выпускать сертификаты для произвольных имён хостов. Поэтому исправление
хранилища доверия требуется и при фиксированном адресе API.

Эта таблица описывает старое решение, а не разрешает оставлять находки
после обновления. Исправленные записи удалены из списка исключений;
текущие результаты и границы проверки — в [VERIFICATION.md](VERIFICATION.md).

## Как повторить обновление безопасности

```bash
# 1. Проверить общую границу, точечные даты и нижние границы в pyproject.toml.
# 2. Пересобрать lock только для выбранных пакетов и прочитать diff.
uv lock --upgrade-package streamlit --upgrade-package pillow --upgrade-package certifi --upgrade-package opentelemetry-api
uv lock --check
uv sync --locked
# 3. Удалить только исключения для исправленных находок и повторить аудит.
uv run python scripts/audit_dependencies.py
# 4. Полная проверка, как в CI.
uv run ruff check . && uv run mypy app ui tests migrations
TEST_DATABASE_URL=… uv run pytest --cov
docker compose up --build --detach --wait
```

Аудит после обновления сам напомнит удалить исключения: запись для
исправленной уязвимости становится «stale» и роняет проверку. Изменения
lock, `pyproject.toml` и `audit-exceptions.json` фиксируются одним коммитом.

## Обновление в обычном порядке

1. Сдвинуть общую `exclude-newer` (не ближе 14 дней); точечные даты не расширять без отдельного обоснования безопасности.
2. `uv lock --upgrade` — обновить всё в пределах границ `pyproject.toml`,
   или `--upgrade-package <имя>` — один пакет.
3. Прочитать diff `uv.lock`: какие версии изменились.
4. Аудит, Ruff, mypy, тесты с покрытием, стенд Docker.
5. Отдельный коммит «Update dependencies to …».

В первом проекте те же шаги выполняет еженедельный workflow, который
открывает pull request. Здесь обновление ручное: проект завершён,
и автоматизация — возможное развитие.
