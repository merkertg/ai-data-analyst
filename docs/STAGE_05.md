# Этап 05. Поиск необычных событий и проверка сценариев

На этапе 04 проект научился точно отвечать на вопрос «сколько?»: считать
продажи, возвраты, выручку и вклады групп. Теперь появляется следующий
вопрос: «какие наблюдения стоит проверить внимательнее?» Этап 05 добавляет
статистические правила, Isolation Forest и отдельную проверку покрытия
внедрённых сценариев.

Короткая инструкция на английском — [Anomaly detection](instructions/anomalies.md),
решение об архитектуре — [ADR 0005](adr/0005-anomaly-detection-and-offline-evaluation.md).
Фактические результаты проверок находятся в [VERIFICATION.md](VERIFICATION.md),
выполненные шаги — в [журнале](DEVELOPMENT_LOG.md).

## 1. Что уже работает

Детектор читает текущую PostgreSQL и возвращает кандидатов на аномалии.
Он ищет необычное количество проданных товаров, скидки, долю возвратов,
крупные позиции заказов и несколько дней нулевого остатка подряд.
Isolation Forest дополняет правила поиском необычных сочетаний признаков.

LLM в этом этапе не участвует. Не нужны ключ OpenAI, запущенный HTTP-сервер
или новый маршрут API. REST API аналитики — следующий этап 06, агент — 07.

Кандидат означает: «это наблюдение отличается от выбранного ориентира».
Он ещё не означает ошибку данных, мошенничество, убыток или доказанную
причину падения продаж. Например, большой заказ может оказаться нормальной
закупкой нового клиента.

## 2. Как запустить

Нужны мигрированная база и данные. Полная подготовка описана в
[Quickstart](instructions/quickstart.md). Для поиска помесячных отклонений
подходит полный набор этапа 03 за январь–сентябрь 2026 года. Маленький набор
`app.db.sample` нужен для ручных SQL-упражнений: истории для модели в нём
недостаточно.

```bash
uv sync --locked
uv run python -m app.analytics.anomalies \
  --start 2026-01-01 --end 2026-10-01 \
  --output /tmp/anomalies.json
```

CLI использует `DATABASE_URL` из настроек проекта. Даты означают
полуоткрытый интервал `[start, end)` по Москве: первое января включено,
первое октября исключено. Все запросы выполняются в одной транзакции
`REPEATABLE READ READ ONLY`: результаты относятся к одному снимку базы,
строки в базе не меняются.

`--seed 42` — исходное значение для воспроизводимости Isolation Forest.
Без `--output` JSON печатается в терминал. Путь отчёта должен быть новым:
существующий файл CLI не перезаписывает. При повторном запуске выбери
другое имя или не указывай `--output`.
Полный список аргументов:

```bash
uv run python -m app.analytics.anomalies --help
uv run python -m app.analytics.evaluate --help
```

Помесячная статистика и Isolation Forest используют только полные
календарные месяцы. Половина сентября содержит меньше дней, чем август:
сравнивать их суммарные количества без поправки некорректно. SQL-признаки
сохраняют обрезанные граничные месяцы, но месячные детекторы их пропускают.
Правила отдельных позиций и склада работают в пределах всего запроса.
Прогноз за полный месяц не строится.

## 3. Откуда берутся признаки

Признак — число, которым описывается наблюдение. Для месяца и категории
это, например, количество товаров или отношение возвратов к продажам.
Для месяца, региона и категории — ещё и доля скидки.

Продажи учитываются по дате оплаты, возвраты — по дате обработки, как в
[этапе 04](STAGE_04.md). SQL отдельно агрегирует продажи и возвраты: несколько
возвратов одной позиции не должны умножать сумму продаж. Деньги остаются
`NUMERIC` в PostgreSQL и `Decimal` в Python.

Важная граница: модель получает только безразмерные отношения. Например,
точно рассчитанные продажи `200000.00` делятся на медиану `100000.00`, и
получается отношение `2`. Лишь это отношение переводится в `float` для
scikit-learn. Модель не пересчитывает выручку и не округляет деньги.

Нет продаж — нет определённого отношения «возвраты / продажи». Это не ноль.
Возвраты могли относиться к прошлому месяцу, поэтому отношение иногда
превышает единицу. Неопределённые доли и слишком короткие ряды пропускаются.
Счётчики отчёта показывают прочитанные наблюдения, а не число рассчитанных
оценок. Отсутствие кандидата не доказывает нормальное поведение.

В отличие от помесячного ряда этапа 04, признаки аномалий не дорисовывают
пустые группы нулями. Полностью отсутствующий месяц категории не становится
нулевым наблюдением для статистики. Эффективная доля скидки считается как
`(gross - rounded paid sales) / gross`: округление позиции может убрать
номинальную скидку меньше копейки.

## 4. Медиана, MAD и необычный месяц

Медиана — середина отсортированного ряда. Для `98, 100, 100, 101, 102`
она равна `100`. Один очень большой заказ сдвинет среднее сильнее, чем
медиану, поэтому медиана удобна как устойчивый ориентир.

Для каждого проверяемого месяца код берёт **другие месяцы того же ряда**.
Сам проверяемый месяц не участвует в собственном ориентире. Такой способ
называется leave-one-out. Нужно хотя бы шесть других наблюдений.

MAD — медиана абсолютных отклонений от медианы. Код использует оценку:

```text
z = 0.6745 * (observed - median) / MAD
candidate when abs(z) >= 6
```

Проверяются помесячное количество оплаченных товаров и доля возвратов
по категории, а также доля скидки по паре «регион — категория».
Отклонение может быть и вниз, и вверх.

Пример: ориентир количества — `100`, MAD — `2`, проверяемое значение — `60`.
Получается `z = -13.49`: по модулю это больше 6, значит, появляется кандидат.
Это учебный расчёт формулы, а не записанный результат полного demo.
Поле `score` отчёта хранит положительный модуль: здесь `13.49`.

### Что делать при MAD = 0

Если остальные месяцы одинаковы, делить на ноль нельзя. Тогда действует
явное запасное правило:

```text
abs(observed - median) > max(abs(median) * 0.25, floor)
floor = 1 for quantity, 0.01 for rates
```

При ориентире `100` порог разницы — `25`: значение `75` не проходит строгое
условие `>`, а `74` проходит. Для долей `0.01` означает один процентный
пункт, а не изменение на один процент от прежней доли.

Эти настройки прозрачны, но выбраны для учебного проекта. Их нельзя
считать готовыми промышленными нормативами. Метод ретроспективный: ориентир
может включать месяцы, которые идут после проверяемого. Это не прогноз
и не проверка на неизвестном будущем периоде.

## 5. Крупная позиция заказа: IQR

Месячная сумма может скрыть один огромный заказ. Поэтому отдельно
проверяется количество в оплаченных позициях каждой категории.
Нужно хотя бы восемь позиций.

`Q1` и `Q3` — нижний и верхний квартили, `IQR = Q3 - Q1`. Кандидатом
становится позиция, количество которой **выше** `Q3 + 3 * IQR`.
Равенства порогу недостаточно.

Например, при `Q1 = 2`, `Q3 = 4` получаем `IQR = 2` и порог `10`:
количество `11` необычно по правилу, `10` — нет. Этот пример поясняет
порог, а не задаёт квартили для реальных строк demo.

Большое количество — повод посмотреть заказ и клиента. Цена товара,
прибыльность и законность операции из этого правила не следуют.

## 6. Нулевой остаток несколько дней подряд

Правило склада проще статистики: три или больше последовательных дня
с остатком `0` дают кандидата. В отчёт попадает максимальный непрерывный
отрезок, а не отдельные перекрывающиеся тройки дней.

```text
10 Sep: 0, 11 Sep: 0, 12 Sep: 0, 13 Sep: 5  -> one 3-day run
10 Sep: 0, 11 Sep: no snapshot, 12 Sep: 0    -> no continuous run
```

Пропуск снимка разрывает последовательность. Отсутствующий снимок
не доказывает нулевой остаток. Начало и конец выбранного периода также
ограничивают наблюдаемую последовательность.

Совпадение нулевых остатков и падения продаж насосов не доказывает связь.
Для проверки причины потребуются дополнительные данные: доступность
остальных моделей, невыполненные заказы, цены, спрос и сроки поставок.

## 7. Что добавляет Isolation Forest

Простые правила рассматривают отдельное число. Isolation Forest ищет
необычные сочетания чисел. У него нет списка A01–A05 и готовых правильных
ответов.

Одна строка модели — месяц, регион и категория. Четыре признака:

1. Количество / медиана количества того же ряда.
2. Продажи / медиана продаж того же ряда.
3. Доля скидки, взвешенная по исходной стоимости позиций.
4. Возвраты / продажи.

Относительные величины помогают сравнивать категории разных масштабов:
большая обычная продажа насосов сама по себе не должна означать то же,
что резкий рост датчиков относительно их обычного уровня.

Модель запускается при наличии хотя бы 16 пригодных строк. Настройки:
100 деревьев, `random_state=42`, `n_jobs=1`, `contamination="auto"`.
Кандидат — строка с отрицательным `decision_function`.
В JSON поле `score` содержит противоположное положительное число:
например, решение `-0.05` превращается в оценку `0.05`.

Оценка модели не является вероятностью аномалии: `-0.05` не значит
«вероятность 5%». Она также не равна размеру потерь. Модель обучается
и оценивает предоставленный период; отдельной неизвестной выборки здесь
нет. При изменении данных или версий зависимостей результат может измениться.

## 8. Почему правильные ответы лежат отдельно

Генератор этапа 03 сохраняет `ground_truth.json`, где описаны пять
внедрённых событий. Если детектор прочитает этот файл, проверка потеряет
смысл: он сможет просто переписать ответы.

Поэтому рабочая цепочка устроена так:

```text
PostgreSQL -> exact features -> rules / Isolation Forest -> anomalies.json

anomalies.json + ground_truth.json -> separate offline coverage evaluation
```

Только отдельная команда сопоставляет кандидатов с периодами и измерениями
из эталона:

```bash
uv run python -m app.analytics.evaluate \
  --report /tmp/anomalies.json \
  --ground-truth data/demo/ground_truth.json
```

Отчёт и эталон должны относиться к одному набору данных и подходящему
периоду. Для полного demo используется январь–сентябрь 2026 года.

| Сценарий | Что внедрено | Какой сигнал позволяет проверить |
| --- | --- | --- |
| A01 | Меньшее количество оплаченных насосов в сентябре | Необычное месячное количество |
| A02 | Скидки 35% на арматуру на Юге в августе | Необычная доля скидки по региону и категории |
| A03 | Дополнительные возвраты по компрессорам в июле | Необычная доля возвратов |
| A04 | Нулевой остаток одного насоса 10–19 сентября | Непрерывный складской отрезок |
| A05 | Оплаченная позиция датчиков на 500 единиц в июне | Необычно большое количество в позиции |

В локальном полном запуске 21 октября 2026 года найдено 33 кандидата:
7 по устойчивой помесячной статистике, 1 по IQR, 1 по складскому правилу,
24 по Isolation Forest. Прочитано 324 месячных наблюдения, 35 171 оплаченная
позиция и 17 472 складских снимка. Отдельная оценка покрыла **5 из 5**
сценариев; соответствия дали статистика и правила. Это результат всей
цепочки, а не качество отдельно взятого Isolation Forest. Два запуска
с seed 42 дали одинаковый JSON. Полная запись — в
[отчёте проверки](VERIFICATION.md).

## 9. Что можно заключить из покрытия

Покрытие отвечает на узкий вопрос: для скольких из пяти известных
внедрённых событий найден подходящий кандидат? Даже `5 / 5` не означает
«точность модели 100%».

В эталоне нет полного списка обычных наблюдений. Поэтому нельзя честно
посчитать precision, долю ложных срабатываний или независимое качество
модели. Дополнительный кандидат может быть как естественной редкостью,
так и нежелательным срабатыванием: его нужно исследовать.

Одно событие могут отметить несколько методов. Один метод может найти
несколько наблюдений внутри сценария. Число кандидатов, число покрытых
сценариев и качество на будущих данных — разные вещи.

## 10. Как читать результат и проверять код

Для каждого кандидата посмотри метод, период, категорию/регион/товар,
наблюдаемое значение, ориентир, порог или оценку модели. После этого
проверь исходные строки. Разделяй измеренный факт и гипотезу о причине.

Общие поля JSON: `schema_version`, `period`, `seed`, `observations`,
`configuration`, `finding_count`, `findings`. Счётчики наблюдений разделены
на месяцы (`monthly`), позиции (`lines`) и склад (`stock`). В кандидате
есть `id`, `method`, `kind`, `period`, `entity`, `metric`, `observed`,
`baseline`, `score`. Денежные и другие `Decimal`-значения записываются
строками, чтобы JSON не превратил точное число в двоичный `float`.

Отдельная оценка возвращает `total_scenarios`, `detected_scenarios`,
`missed_scenarios`, `coverage_percent`, `matches`, `note`. В `matches`
идентификаторы A01–A05 связаны с идентификаторами подходящих кандидатов.

| Файл | За что отвечает |
| --- | --- |
| `app/analytics/anomaly_models.py` | Типы признаков и результатов |
| `app/analytics/anomaly_features.py` | Точные SQL-признаки из текущей базы |
| `app/analytics/detection.py` | Статистические правила, складские отрезки, Isolation Forest |
| `app/analytics/anomalies.py` | CLI: даты, снимок базы и JSON-отчёт |
| `app/analytics/evaluate.py` | Отдельная проверка покрытия сценариев по эталону |

Полная инструкция — [Testing](instructions/testing.md). Проверяются
обычные и необычные примеры, равенство порогу, MAD = 0, короткая история,
разрывы складских дней, повторяемость модели, точность SQL, даты и
отдельная оценка эталона.

```bash
uv run pytest tests/test_detection.py tests/test_anomalies_cli.py \
  tests/test_anomaly_evaluation.py
uv run pytest tests/integration/test_anomaly_features.py
uv run ruff check .
uv run ruff format --check .
uv run mypy app tests migrations
uv run pytest -m "not integration"
uv run pytest -m integration
```

Интеграционные тесты запускаются только через `TEST_DATABASE_URL` с именем
базы, оканчивающимся на `_test`. Они не берут адрес разработки из `.env`.
Без переменной локально тесты пропускаются; при `CI=true` это ошибка.
Локальные проверки и фактический запуск GitHub Actions подтверждаются
отдельно для конкретного состояния кода.
