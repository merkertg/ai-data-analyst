# Этап 06. REST API аналитики

На этапах 04 и 05 точные показатели и поиск аномалий запускались из
терминала. Теперь те же расчёты доступны по HTTP: любой клиент — браузер,
будущий интерфейс Streamlit или AI-агент — получает их одним запросом
и в одном формате. Новых формул нет: API только принимает запрос,
проверяет его, вызывает готовые функции и возвращает JSON.

Короткая инструкция на английском — [Using the API](instructions/usage.md),
решение об архитектуре — [ADR 0006](adr/0006-rest-api-and-saved-reports.md).
Фактические результаты — в [VERIFICATION.md](VERIFICATION.md), выполненные
шаги — в [журнале](DEVELOPMENT_LOG.md). Наглядно — в [PDF](guide/ai-data-analyst-guide.pdf).

## 2. Эндпоинты

| Метод и путь | Параметры | Что возвращает |
| --- | --- | --- |
| `GET /api/metrics/revenue` | `start`, `end`; по желанию `compare_start`, `compare_end` | Продажи, возвраты, чистая выручка, помесячный ряд, сравнение |
| `GET /api/metrics/orders` | те же | Оплаченные заказы, средний чек, помесячный ряд, сравнение |
| `GET /api/analytics/categories` | `start`, `end`, `compare_start`, `compare_end` — все обязательны | Итоги обоих периодов, общее изменение, вклады категорий |
| `GET /api/analytics/regions` | те же | То же по регионам клиентов |
| `GET /api/analytics/anomalies` | `start`, `end`; по желанию `seed` (по умолчанию 42) | Кандидаты на аномалии этапа 05 |
| `POST /api/reports` | JSON: `kind` = `comparison` или `anomalies` + параметры | Сохранённый отчёт, `201`, заголовок `Location` |
| `GET /api/reports/{report_id}` | UUID отчёта | Отчёт ровно таким, каким он был сохранён |
| `GET /api/reports` | `limit` (1–100, по умолчанию 20), `offset` | Список отчётов от новых к старым, без тела результата |

Периоды — те же, что на этапе 04: полуоткрытый интервал `[start, end)`
по московскому времени. `start=2026-09-01&end=2026-10-01` — ровно сентябрь.

## 3. Как запустить

Нужны PostgreSQL, миграции и данные (см. [Quickstart](instructions/quickstart.md)).
Этап добавил миграцию `0002`, её нужно применить:

```bash
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

В состоянии кода этапа 06 `/ready` отвечает
`{"status":"ready","revision":"0002"}`; после этапа 07 текущая ревизия
`0003`, которую применяет команда `upgrade head`. Откройте
<http://127.0.0.1:8000/docs>: все маршруты сгруппированы по разделам
`metrics`, `analytics`, `reports`, у каждого есть кнопка **Try it out**.

Те же запросы через curl:

```bash
curl "http://127.0.0.1:8000/api/metrics/revenue?start=2026-09-01&end=2026-10-01&compare_start=2026-08-01&compare_end=2026-09-01"
curl "http://127.0.0.1:8000/api/analytics/categories?start=2026-09-01&end=2026-10-01&compare_start=2026-08-01&compare_end=2026-09-01"
curl "http://127.0.0.1:8000/api/analytics/anomalies?start=2026-01-01&end=2026-10-01"
```

Сохранить отчёт:

```bash
curl -i -X POST http://127.0.0.1:8000/api/reports \
  -H 'Content-Type: application/json' \
  -d '{"kind":"comparison","start":"2026-09-01","end":"2026-10-01","compare_start":"2026-08-01","compare_end":"2026-09-01","dimension":"category"}'
```

Ответ — `201 Created` и `location: /api/reports/<uuid>`; по этому адресу
отчёт можно получить позже.

## 4. Параметры и проверка запроса

Параметры описаны Pydantic-моделями в `app/schemas/analytics.py`.
FastAPI собирает из строки запроса объект модели и проверяет его до того,
как маршрут начнёт работу:

```python
class PeriodQuery(BaseModel):
    model_config = ConfigDict(extra="forbid")

    start: date
    end: date

    @model_validator(mode="after")
    def validate_period(self) -> Self:
        check_interval(self.start, self.end, "period")
        return self
```

- `start: date` — строка `2026-13-01` не дата, ответ `422`.
- `check_interval` отклоняет пустой и обратный период и периоды длиннее
  120 календарных месяцев (тот же предел, что у помесячного ряда).
- `extra="forbid"` — неизвестный параметр (`?strat=…` с опечаткой) тоже
  `422`, а не тихо проигнорированная ошибка.
- Для `revenue` и `orders` сравнение необязательно, но `compare_start`
  и `compare_end` задаются только вместе. Для `categories` и `regions`
  оба обязательны: вклады без сравнения не имеют смысла.
- `seed` для аномалий — целое от 0 до 4 294 967 295.

Маршрут получает модель так: `query: Annotated[ComparisonQuery, Query()]`.
Ответ `422` содержит список ошибок с указанием поля, например:

```json
{"detail": [{"type": "missing", "loc": ["query", "compare_start"], "msg": "Field required"}]}
```

## 5. Внедрение зависимостей: сессия базы

Маршрут не открывает соединение сам. Он объявляет, что ему нужно:

```python
@router.get("/revenue")
def revenue(
    session: ReadSession, query: Annotated[OptionalComparisonQuery, Query()]
) -> RevenueResponse:
    return analytics.revenue(session, query)
```

`ReadSession` — это `Annotated[Session, Depends(read_session)]`. FastAPI
вызывает `read_session()` перед маршрутом и закрывает сессию после ответа.
Это и есть **dependency injection**: маршрут получает готовую зависимость,
а тест может подменить её через `app.dependency_overrides` — так
интеграционные тесты подставляют сессию тестовой базы `*_test`.

Две зависимости:

| Зависимость | Где | Транзакция |
| --- | --- | --- |
| `ReadSession` | Все `GET` | `REPEATABLE READ READ ONLY`: все запросы одного ответа видят один снимок данных, запись запрещена самой PostgreSQL |
| `WriteSession` | `POST /api/reports` | Обычная; маршрут сам вызывает `commit()`, ошибка — `rollback()` |

### Найденная ловушка: ленивая сессия

Первый вариант открывал сессию сразу. Тесты показали проблему: FastAPI
вычисляет зависимости **даже когда параметры запроса неверны**. Значит,
запрос с перепутанными датами всё равно обращался к базе, а при
недоступной базе получал `503` вместо понятного `422`.

Решение — `LazySession`: сессия выбирает соединение только при первом
SQL-запросе (метод `get_bind`). Неверный запрос отклоняется раньше,
маршрут не запускается, база не трогается. Проверено на настоящем
сервере с недоступной базой: корректный запрос — `503`, неверный — `422`.

### Почему маршруты — `def`, а не `async def`

На этапе 01 мы обещали вернуться к `async`. Маршруты этапа 06 остаются
обычными функциями, и это осознанно:

- SQLAlchemy `Session` и драйвер psycopg здесь синхронные: вызов ждёт
  ответа PostgreSQL и блокирует поток;
- обычную `def`-функцию FastAPI запускает в пуле потоков (по умолчанию
  до 40 одновременно), поэтому ожидание базы не останавливает остальные
  запросы;
- если объявить маршрут `async def` и внутри вызвать синхронную сессию,
  ожидание базы заблокирует цикл событий — и весь сервер перестанет
  отвечать, пока идёт запрос.

`async def` имеет смысл вместе с асинхронным драйвером и `AsyncSession`.
Для локального API с запросами по 15–180 мс это лишняя сложность.
Вернуться к вопросу стоит, когда появится много долгих внешних вызовов,
например к LLM на этапе 07.

## 6. Ответы: схемы и точные деньги

Ответы тоже описаны моделями (`RevenueResponse`, `ContributionsResponse`
и т. д.). Аннотация возврата маршрута `-> RevenueResponse` делает три вещи:
задаёт схему в `/docs`, проверяет ответ и сериализует его.

- **Деньги — строки.** `Decimal("468349280.42")` превращается в JSON
  `"468349280.42"`, а не в число с плавающей точкой: клиент не потеряет
  копейки. Так же было в CLI этапа 04.
- **Неопределённое — `null`.** Средний чек без оплаченных заказов,
  процент от нулевой базы, вклад при нулевом общем изменении.
- **`from_attributes=True`** позволяет модели прочитать значения прямо
  из dataclass-результатов `app/analytics` — без ручного копирования полей.
- Каждый ответ содержит `"currency": "RUB"` и `"timezone": "Europe/Moscow"`.

## 7. Ошибки

| Код | Когда | Тело |
| --- | --- | --- |
| `422` | Неверные параметры или тело запроса | Список ошибок по полям |
| `404` | Отчёта с таким UUID нет | `{"detail":"Report not found"}` |
| `503` | `DATABASE_URL` не задан или база недоступна | `{"detail":"Database is not ready"}` |
| `500` | Непредвиденная ошибка | `Internal Server Error`, без подробностей |

Текст `503` одинаков для всех причин: адрес базы и сообщения драйвера
не уходят клиенту. Обработчики зарегистрированы в `app/api/errors.py`
(`DatabaseNotConfigured`, `OperationalError`, `InterfaceError`).

## 8. Сохранённые отчёты

Отчёт — **снимок**: результат считается один раз и сохраняется. Если позже
появятся новые заказы, живой `GET /api/analytics/categories` покажет новые
числа, а сохранённый отчёт — прежние. Это проверяет тест
`test_report_is_a_snapshot`: после нового заказа на 50 000 живое изменение
стало −241 500.00, а отчёт по-прежнему −291 500.00.

Таблица `reports` (миграция `0002`):

| Столбец | Тип | Смысл |
| --- | --- | --- |
| `id` | `UUID` | Номер отчёта; его нельзя угадать перебором, как 1, 2, 3 |
| `kind` | `VARCHAR(32)` + `CHECK` | `comparison` или `anomalies` |
| `parameters` | `JSONB` | Параметры запроса — чтобы повторить расчёт |
| `result` | `JSONB` | Результат ровно в том виде, в каком его вернул API |
| `app_version` | `VARCHAR(32)` | Версия кода, посчитавшего отчёт |
| `created_at` | `timestamptz` | Время сохранения (`now()` в PostgreSQL) |

У `reports` нет внешних ключей на таблицы продаж: отчёт хранит числа,
а не ссылки на строки, которые могут измениться. Откат `downgrade 0001`
удаляет только эту таблицу.

Тело `POST` выбирает модель по полю `kind` (discriminated union): для
`comparison` нужны оба периода и `dimension`, для `anomalies` — период
и `seed`. Неизвестный `kind` или лишнее поле — `422`.

## 11. Ограничения

- **Нет аутентификации.** API рассчитан на локальный запуск
  (`127.0.0.1`). Права доступа и роли — этап 09.
- `GET /api/analytics/anomalies` считает заново при каждом запросе
  (~0,2 с на 20 000 заказов). Чтобы сохранить результат, используйте
  `POST /api/reports` с `kind: "anomalies"`.
- Список отчётов не сообщает общее число записей; удаления отчётов нет.
- Сохранённый отчёт не пересчитывается: после изменения данных он
  описывает прошлое состояние — так и задумано.

## 12. Проверь себя

1. Почему неверный запрос получает `422`, а не `500` или `503`?
2. Что такое внедрение зависимостей и как его используют тесты?
3. Зачем сессии чтения `REPEATABLE READ` и `READ ONLY`?
4. Почему деньги в JSON — строки?
5. Чем живой ответ `categories` отличается от сохранённого отчёта?
6. Зачем `LazySession`, если сессию можно открыть сразу?

<details>
<summary>Ответы</summary>

1. Pydantic-модель параметров проверяет запрос до маршрута; FastAPI
   превращает ошибки проверки в `422` со списком полей. Ленивая сессия
   не даёт неверному запросу дойти до базы.
2. Маршрут объявляет зависимость (`Depends`), FastAPI создаёт её перед
   вызовом. Тест подменяет её через `app.dependency_overrides`, например
   сессией тестовой базы.
3. Все запросы одного ответа видят одно состояние данных, а случайная
   запись невозможна — PostgreSQL отклонит её.
4. Число с плавающей точкой может исказить копейки; строка передаёт
   `Decimal` точно.
5. Живой ответ считается по текущим данным, отчёт — снимок на момент
   сохранения и потом не меняется.
6. FastAPI вычисляет зависимости даже для неверного запроса; ленивая
   сессия подключается только при первом SQL и не трогает базу зря.

</details>

### Самостоятельное задание

Добавь в `GET /api/reports` необязательный фильтр `kind`

интеграционный тест: два отчёта разных видов, фильтр возвращает один.
