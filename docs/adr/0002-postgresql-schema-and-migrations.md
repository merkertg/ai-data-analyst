# ADR 0002: PostgreSQL schema, integrity rules and migrations

- **Status:** Accepted
- **Date:** 2026-10-20

## Context

The analyst must compute exact financial metrics from corporate data: orders, order items, refunds, customers, products and inventory. Later stages generate a dataset with injected anomalies and let an LLM call analytics tools over this data. Wrong or inconsistent rows would silently corrupt every metric, and the schema will evolve over ten stages.

## Decision

- **PostgreSQL 17** in Docker Compose for development (`db`, persistent volume) and a separate disposable `db-test` (`tmpfs`, database name ending with `_test`). The image is pinned by digest in Compose and CI.
- **Six normalised tables**: `customers`, `products`, `orders`, `order_items`, `refunds`, `inventory_snapshots`. An order and its lines are separate tables (one-to-many); the sale price is stored on the line.
- **Integrity in the database**, not only in Python: `NOT NULL`, 14 `CHECK` constraints (including cross-column rules such as `(status = 'paid') = (paid_at IS NOT NULL)`), `UNIQUE` on SKU, order line and daily snapshot, and foreign keys with explicit delete rules: `CASCADE` from orders to their lines, `RESTRICT` everywhere else to protect history.
- **A naming convention** for all constraints and indexes, so errors name the violated rule and migrations can drop constraints by name.
- **Exact money and time types**: `NUMERIC(12, 2)` read as `Decimal`, discount as `NUMERIC(5, 4)` fraction, `timestamptz` for events; reporting months are computed in `Europe/Moscow`.
- **Alembic migrations** as the only way to create the schema (no `create_all`), autogenerated and then reviewed. Applied migrations are never edited. CI runs `upgrade head`, `alembic check` and a `downgrade base`/`upgrade head` round trip.
- **SQLAlchemy 2** typed models (`Mapped[...]`) with psycopg 3; a lazily created engine with `pool_pre_ping` and a 3-second connect timeout.
- **`GET /ready`** checks the connection and compares `alembic_version` with the latest migration; any failure returns the same `503` without details.

## Consequences

- Invalid rows are rejected even when inserted by scripts or psql; tests assert the exact constraint name for 20 invalid cases.
- Rules spanning several tables (refunds not exceeding the line total, refunds only for paid orders) cannot be expressed as `CHECK` and must be verified by data quality checks in Stage 03.
- `RESTRICT` means deleting customers, products or refunded lines requires an explicit data procedure; this is intended for financial history.
- Integration tests need Docker locally; without `TEST_DATABASE_URL` they are skipped locally and fail on CI.
