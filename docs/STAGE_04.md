# Этап 04. Детерминированная аналитика и сравнение периодов

Теперь проект умеет отвечать на точные вопросы к базе: сколько было продаж,
сколько вернули покупателям, как изменилась выручка и какие категории или
регионы дали этот результат. Числа вычисляют SQL и Python с `Decimal`.
LLM и поиска аномалий здесь ещё нет: сначала нужен надёжный измерительный
инструмент, на который смогут опираться следующие этапы.

Короткая английская инструкция: [Analytics](instructions/analytics.md).
Решение по архитектуре: [ADR 0004](adr/0004-deterministic-analytics-core.md).
Проверенные результаты: [VERIFICATION.md](VERIFICATION.md).
Обе наглядные версии: [русский PDF](guide/ai-data-analyst-guide.pdf) и
[английский PDF](guide/ai-data-analyst-guide-en.pdf).

## 1. Что добавлено

| Часть | Для чего нужна |
| --- | --- |
| `app/analytics/models.py` | Проверенные границы периода и типизированные результаты с `Decimal` |
| `app/analytics/` | Расчёт сводки, месяцев, сравнения и вкладов групп |
| `python -m app.analytics` | Получить результаты в JSON без запуска API |
| Тесты аналитики | Сверить SQL с ручными ответами, проверить границы и особые случаи |

Новых зависимостей нет. PostgreSQL уже умеет фильтровать, группировать и
суммировать точные денежные значения. Python с `Decimal` рассчитывает
отношения, округление и представление результата. Pandas и DuckDB отложены
до задачи, в которой они действительно понадобятся; это зафиксировано в ADR.

```text
даты и измерение category / region
                 │
                 ▼
       CLI или функция Python
                 │
                 ▼
 PostgreSQL: продажи, число заказов и возвраты отдельно
                 │
                 ▼
 Decimal: выручка, средний чек, разница и проценты
                 │
                 ▼
 JSON: суммы строками, неопределённые значения null
```

## 2. Что означает период

Период задаётся двумя датами: `[start, end)`. Квадратная скобка означает,
что начало включено; круглая — что конец не включён. Все границы — полночь
по `Europe/Moscow`, независимо от часового пояса компьютера или PostgreSQL.

Например, `--start 2026-09-01 --end 2026-10-01` выбирает весь сентябрь.
Оплата ровно 1 сентября в 00:00 входит, а ровно 1 октября в 00:00 уже нет.
Поэтому соседние месяцы не теряют и не дублируют пограничную операцию.
`Period.month(2026, 9)` создаёт такой же календарный месяц из Python.
Пустой или обратный интервал запрещён.

Заказ из маленького учебного набора оплачен 1 октября в 01:30 по Москве.
В UTC это ещё 30 сентября, но отчётная операция относится к октябрю.
Здесь важно бизнес-правило, а не настройка часов на машине.

`monthly_metrics` разбивает период на календарные месяцы и сохраняет пустые
месяцы с нулями. Для периода с 15 сентября до 10 ноября получатся три
отрезка: 15 сентября — 1 октября, 1 октября — 1 ноября, 1 ноября — 10 ноября.
Первый и последний месяцы обрезаны границами запроса. Разрешено не более
120 календарных отрезков — десяти лет помесячного отчёта.

## 3. Пять показателей

Все суммы — в рублях, без НДС. `pending` и `cancelled` не дают продаж.

| Поле результата | Смысл |
| --- | --- |
| `paid_sales` | Продажи оплаченных заказов по дате `paid_at` |
| `refunds` | Возвраты по дате `processed_at`, только по оплаченным заказам |
| `net_revenue` | Продажи минус возвраты |
| `paid_orders` | Количество оплаченных заказов, каждый считается один раз |
| `average_order_value` | Продажи / оплаченные заказы, до вычета возвратов |

Сначала округляется каждая строка заказа:

```text
сумма позиции = ROUND(quantity × unit_price × (1 − discount), 2)
продажи = сумма округлённых позиций
чистая выручка = продажи − возвраты
средний чек = продажи / число оплаченных заказов
```

Например, две позиции по 0,005 после расчёта скидки дают 0,01 + 0,01 = 0,02.
Если сначала сложить неокруглённые значения, получится 0,01 — другой ответ.
Поэтому порядок округления является частью контракта, а не оформлением.

Средний чек округляется до копеек с `ROUND_HALF_UP`: половина шага
округляется от нуля. Если оплаченных заказов нет, средний чек равен `None`
в Python и `null` в JSON: деление на ноль не имеет смысла. Все остальные
показатели пустого периода — нули. В периоде только с возвратами чистая
выручка может быть отрицательной, а среднего чека всё равно не будет.

Возврат уменьшает выручку в месяце его проведения. Если товар оплатили
в сентябре, а деньги вернули в октябре, продажа остаётся в сентябре,
возврат относится к октябрю. Фильтровать возврат по месяцу оплаты нельзя.

## 4. Почему запросы разделены

У заказа может быть несколько позиций, у позиции — несколько возвратов.
Если соединить всё одним прямым `JOIN`, одна продажа повторится на каждый
возврат. Число строк соединения тоже не равно числу заказов.

Поэтому продажи, число оплаченных заказов и возвраты агрегируются отдельно.
Затем готовые результаты объединяются. Число заказов читается из `orders`,
а не выводится из количества позиций. Группы для сравнения берутся из обоих
периодов, включая категории или регионы только с возвратами.

Это продолжение упражнения [SQL вручную](STAGE_02.md): проверяемые запросы
теперь оформлены как функции, пригодные для дальнейшего API и агента.

## 5. Как запустить

Команды выполняются из корня проекта. Нужны запущенная PostgreSQL,
применённые миграции и данные; подготовка описана в [Quickstart](instructions/quickstart.md).
CLI читает `DATABASE_URL` из настроек проекта. Сервер FastAPI запускать не нужно.

Сводка за сентябрь и помесячный ряд:

```bash
uv run python -m app.analytics --start 2026-09-01 --end 2026-10-01
```

Сравнение сентября с августом и вклады категорий:

```bash
uv run python -m app.analytics \
  --start 2026-09-01 --end 2026-10-01 \
  --compare-start 2026-08-01 --compare-end 2026-09-01 \
  --dimension category
```

Для регионов замени `category` на `region`. Принимаются только эти два
значения; имя таблицы, столбца или SQL в этот параметр передать нельзя.
Параметры `--compare-start` и `--compare-end` задаются вместе. Без них
сводка и месяцы заполнены, `comparison` равен `null`, `contributions` — пустой список. Справка:

```bash
uv run python -m app.analytics --help
```

Денежные значения и проценты в JSON передаются строками, например
`"309000.00"`; количество заказов — целым числом; отсутствующий результат —
`null`. Так JSON не заставляет превращать точные деньги в `float`.
Все запросы одного вызова выполняются в одной транзакции
`REPEATABLE READ READ ONLY`: отчёт видит согласованное состояние базы,
даже если параллельно кто-то сохраняет новые операции.

Функции принимают готовую SQLAlchemy-сессию. При вызове из другого кода
границы и изоляцию транзакции выбирает вызывающий код. Модуль не читает
`ground_truth.json`, не вызывает LLM и не меняет бизнес-данные.

## 6. Ручной пример: маленький набор сентября и октября

Этот пример относится к `app.db.sample` из этапа 02. Он не описывает большой
набор из 20 000 заказов. Учебный и большой наборы загружаются в разные
пустые базы; существующие данные удалять для этого примера не требуется.

| Показатель | Сентябрь | Октябрь |
| --- | ---: | ---: |
| Продажи | 310 000,00 | 18 000,00 |
| Возвраты | 1 000,00 | 500,00 |
| Чистая выручка | 309 000,00 | 17 500,00 |
| Оплаченные заказы | 2 | 1 |
| Средний чек | 155 000,00 | 18 000,00 |

Сентябрь: два насоса со скидкой дают 180 000, ещё один насос — 120 000,
пять датчиков — 10 000. Всего 310 000. Сентябрьский возврат по датчикам
равен 1 000, поэтому чистая выручка — 309 000. В октябре оплачена арматура
на 18 000 и проведён ещё один возврат по сентябрьским датчикам на 500:
18 000 − 500 = 17 500.

Для этого набора сравни октябрь с сентябрём:

```bash
uv run python -m app.analytics \
  --start 2026-10-01 --end 2026-11-01 \
  --compare-start 2026-09-01 --compare-end 2026-10-01 \
  --dimension category
```

## 7. Как читать сравнение

```text
изменение = текущий показатель − предыдущий показатель
изменение, % = изменение / abs(предыдущий показатель) × 100
```

Октябрьская чистая выручка: 17 500 − 309 000 = −291 500 рублей,
или −94,34%. Продажи изменились на −292 000, возвраты — на −500,
число заказов — на −1. Меньше возвратов арифметически смягчает снижение
чистой выручки, хотя абсолютные продажи упали сильнее.

В знаменателе процента берётся модуль прошлого значения. Для прошлой
выручки −100 и текущей −50 улучшение составит +50%. При прошлом значении
0 процент равен `null`: ни рост с нуля до 100, ни пара нулей не превращаются
в выдуманный конечный процент. Если в одном из периодов нет среднего чека,
его разница и процент тоже равны `null`.

Периоды могут пересекаться или иметь разную длительность. Функция сравнит
их суммы без пересчёта «на день». Осмысленность выбранных периодов зависит
от вопроса; сравнение месяца с неделей само по себе не учитывает эту разницу.

## 8. Вклады категорий и регионов

Вклад показывает, какую часть общего изменения даёт изменение отдельной
группы. Для категории используются категории товаров, для региона — регион
клиента. Сначала вычисляется чистая выручка каждой группы в обоих периодах.

```text
разница группы = текущая выручка группы − прошлая выручка группы
вклад, % = разница группы / общая разница × 100
```

| Категория, октябрь к сентябрю | Разница выручки | Вклад |
| --- | ---: | ---: |
| Насосы | −300 000,00 | 102,92% |
| Датчики | −9 500,00 | 3,26% |
| Запорная арматура | +18 000,00 | −6,17% |
| **Всего** | **−291 500,00** | **100,01% после округления** |

Насосы дали больше 100% снижения: их падение частично компенсировано ростом
арматуры. У арматуры отрицательный вклад в общее падение, потому что её
собственная разница положительна, а общая отрицательна. Датчики в октябре
имеют только возврат; категория всё равно входит в результат.

После округления доли могут не складываться ровно в 100%. При нулевом общем
изменении все доли равны `null`, даже если одна группа упала, а другая
выросла на ту же сумму. Группы сортируются по разнице от самой отрицательной
к положительной, затем по названию. Вклад объясняет арифметику, но не причину:
из этих чисел нельзя автоматически заключить, почему покупатели купили меньше.

## 9. Полный набор: сентябрь к августу

Тот же CLI на полном наборе из этапа 03 (seed 42, 20 000 заказов). Набор
загружен в отдельную пустую базу `*_test`, база разработки не менялась:

```bash
uv run python -m app.analytics \
  --start 2026-09-01 --end 2026-10-01 \
  --compare-start 2026-08-01 --compare-end 2026-09-01 \
  --dimension category
```

Фактический результат 21 октября 2026 года:

| Показатель | Август | Сентябрь | Изменение |
| --- | ---: | ---: | ---: |
| Продажи | 633 733 255,24 | 468 349 280,42 | −165 383 974,82 (−26,10%) |
| Возвраты | 1 557 126,03 | 1 670 523,07 | +113 397,04 (+7,28%) |
| Чистая выручка | 632 176 129,21 | 466 678 757,35 | −165 497 371,86 (−26,18%) |
| Оплаченные заказы | 1 985 | 1 931 | −54 (−2,72%) |
| Средний чек | 319 261,09 | 242 542,35 | −76 718,74 (−24,03%) |

| Категория | Разница выручки | Вклад |
| --- | ---: | ---: |
| pumps | −138 597 069,79 | 83,75% |
| compressors | −26 317 759,86 | 15,90% |
| sensors | −294 972,94 | 0,18% |
| valves | −287 569,27 | 0,17% |

Как это читать:

- Число заказов почти не изменилось (−2,72%), а средний чек упал на 24%:
  покупают примерно так же часто, но на меньшие суммы.
- 83,75% падения дают насосы. Это внедрённый сценарий **A01**: в сентябре
  количество в оплаченных позициях насосов уменьшено до 40% от исходного.
  Аналитика нашла его, не читая `ground_truth.json`.
- По регионам падение распределено без явного лидера: от 7,72% (Ural)
  до 18,56% (Central). Это описывает распределение вкладов: оно не доказывает
  причину снижения и не исключает региональные факторы.
- Помесячный ряд за январь–сентябрь показывает и сценарий **A03**: возвраты
  июля — 132 586 941,37 при 0,8–1,7 млн в остальные месяцы.

Это измерение, а не объяснение. Почему упали насосы — нехватка на складе
(сценарий A04), цена или спрос, — из этих чисел вывести нельзя. Автоматический
поиск таких отклонений — задача этапа 05.

## 10. Как проверить

Без базы проверяются периоды, числовые модели, округление и аргументы CLI.
Интеграционные тесты сравнивают настоящую PostgreSQL с ручными ответами и
проверяют отсутствие двойного счёта, возвраты другого месяца, пустые и
частичные месяцы, границы по Москве, сравнения и вклады.

```bash
uv run pytest tests/test_analytics_models.py tests/test_analytics_cli.py
uv run pytest tests/integration/test_analytics.py
uv run ruff check .
uv run ruff format --check .
uv run mypy app tests migrations
```

Интеграционные тесты используют только `TEST_DATABASE_URL` с суффиксом
`_test`. Без переменной локально они пропускаются; при `CI=true` это ошибка.
Полная подготовка — в [Testing](instructions/testing.md). Фактические числа
тестов и результаты smoke-проверки записываются в [отчёт](VERIFICATION.md),
а выполненные шаги — в [журнал](DEVELOPMENT_LOG.md). Удалённый GitHub Actions
подтверждается отдельно для конкретного коммита.
