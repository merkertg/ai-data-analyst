# Этап 10. Docker, CI/CD и публикация

Последний этап курса превращает проект в законченную поставку. Критерий
из плана: другой разработчик клонирует репозиторий, выполняет
`docker compose up --build`, открывает интерфейс и повторяет
демонстрационные сценарии. Ничего настраивать руками не нужно: ни `.env`,
ни загрузки данных, ни выдачи токена.

Этап добавляет:

- **Docker-образ** приложения: один образ запускает миграции, подготовку
  стенда, API и интерфейс;
- **стенд Compose** из пяти сервисов, который сам загружает демо-данные
  и выдаёт интерфейсу токен;
- **CI/CD**: порог покрытия тестами, аудит зависимостей, сборку образа,
  сквозную smoke-проверку стенда и публикацию проверенного образа в GHCR.

Показ проекта — в [демонстрации](DEMO.md), публикация образов — в
[RELEASES.md](RELEASES.md), обновление зависимостей — в
[DEPENDENCY_UPDATES.md](DEPENDENCY_UPDATES.md), решение — в
[ADR 0010](adr/0010-docker-packaging-and-delivery.md). Состояние проекта на
конец курса — в [PROJECT_STATUS_2026-10-22.md](PROJECT_STATUS_2026-10-22.md).

## 1. Что входит в поставку

| Файл | Для чего |
| --- | --- |
| `Dockerfile` | Двухстадийная сборка: зависимости из `uv.lock`, финальный образ без uv и dev-инструментов, пользователь UID 10001 |
| `.dockerignore` | В контекст сборки не попадают `.env`, `.git`, тесты, данные и отчёты |
| `compose.yaml` | `db`, `migrate`, `bootstrap`, `api`, `ui` (+ `db-test` для тестов) |
| `app/bootstrap.py` | Подготовка стенда: проверка схемы, демо-данные в пустую базу, токен интерфейса |
| `ui/config.py` | Токен из файла `UI_API_TOKEN_FILE`; имя сервиса `api` — только из явного списка |
| `scripts/smoke_stack.py` | Сквозная проверка запущенного стенда, только стандартная библиотека |
| `scripts/audit_dependencies.py`, `scripts/audit-exceptions.json` | Аудит уязвимостей с исключениями, у которых есть срок |
| `.github/workflows/ci.yml` | Четыре задания: проверки, аудит, контейнер, публикация |

## 2. Как запустить

```bash
git clone git@github.com:merkertg/ai-data-analyst.git
cd ai-data-analyst
docker compose up --build
```

Через 30–60 секунд (первая сборка дольше — скачиваются базовые образы
и зависимости):

| Адрес | Что там |
| --- | --- |
| <http://127.0.0.1:8502> | Интерфейс: панель, AI-аналитик, отчёты |
| <http://127.0.0.1:8001/docs> | API и его документация |
| `127.0.0.1:5436` | PostgreSQL (для psql и DBeaver) |

Все порты слушают только `127.0.0.1`. Остановить стенд: `Ctrl+C` или
`docker compose down` — данные остаются в томе. Начать с чистого листа:
`docker compose down --volumes`.

## 3. Пять сервисов и порядок запуска

```text
db (PostgreSQL 17, healthy)
 └─► migrate: alembic upgrade head ─► завершился успешно
      ├─► bootstrap: демо-данные в пустую базу + токен интерфейса ─► завершился
      └─► api: uvicorn, /ready healthy
               └─► ui: Streamlit (ждёт api healthy и bootstrap completed)
```

Порядок задают `depends_on` с условиями `service_healthy` и
`service_completed_successfully`. Интерфейс не стартует, пока нет схемы,
данных и токена. Проверки здоровья написаны на стандартной библиотеке
Python: в образе нет curl.

| Сервис | Команда | Что получает |
| --- | --- | --- |
| `db` | образ `postgres:17@sha256:…` | Том `postgres_data` |
| `migrate` | `python -m alembic upgrade head` | Отдельные параметры `DATABASE_*`: адрес, порт, имя базы, пользователь, пароль |
| `bootstrap` | `python -m app.bootstrap --token-file …` | Те же параметры `DATABASE_*`, том `ui_token` |
| `api` | `uvicorn app.main:app` | Те же параметры `DATABASE_*`, настройки модели и лимитов |
| `ui` | `streamlit run ui/main.py` | Адрес API; файл analyst-токена смонтирован **только для чтения**; нет параметров базы и ключа модели |

### Адрес базы и специальные символы в пароле

Уточнение от 22 октября 2026 года: Compose передаёт приложению не готовую
строку адреса, а отдельные значения:

```text
DATABASE_HOST=db
DATABASE_PORT=5432
DATABASE_NAME ← POSTGRES_DB
DATABASE_USER ← POSTGRES_USER
DATABASE_PASSWORD ← POSTGRES_PASSWORD
```

Эти значения получают только `migrate`, `bootstrap` и `api`. В настройках
`app/config.py` функция SQLAlchemy `URL.create(...)` собирает из них адрес
подключения. Поэтому пароль с `@`, `/`, `#` или `%` передаётся в исходном
виде: кодировать символы вручную в `POSTGRES_PASSWORD` не нужно. В `.env`
значение со специальными символами лучше заключить в кавычки. Интерфейс
`ui` не получает ни готового адреса базы, ни его компонентов.

При запуске Python на компьютере `.env.example` использует готовый
`DATABASE_URL` с адресом `127.0.0.1:5436`. Если такой адрес задан явно,
он имеет приоритет над отдельными параметрами в настройках приложения.
В написанном вручную URL специальные символы имени пользователя и пароля
по-прежнему нужно кодировать: `@` → `%40`, `/` → `%2F`, `#` → `%23`,
`%` → `%25`. При изменении пароля PostgreSQL обнови и этот адрес.
Compose не передаёт хостовый `DATABASE_URL` из `.env` внутрь контейнеров.

Для запуска на компьютере можно выбрать и отдельные параметры:
закомментировать `DATABASE_URL`, задать все четыре значения
`DATABASE_HOST`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD`
и установить опубликованный порт `DATABASE_PORT=5436`. Если указан только
один из этих четырёх параметров, настройки отклоняются как неполные.
Подробнее — в [инструкции по базе](instructions/database.md#connection-settings).

## 4. Один образ на всё

Миграции, подготовка, API и интерфейс используют одни и те же зависимости
(Streamlit и Plotly — в основном списке проекта), поэтому образ один,
а сервисы отличаются только командой. Это проще, чем отдельный образ
интерфейса в первом проекте. Цена — интерфейс получает код сервера в образе:
его настройки при этом не содержат ни адреса базы, ни ключа модели (это
проверяет тест).

```dockerfile
FROM python:3.12-slim@sha256:a6e3… AS python-base
FROM python-base AS builder
COPY --from=ghcr.io/astral-sh/uv:0.12.23@sha256:61d3… /uv /bin/uv
RUN uv sync --locked --no-dev            # только runtime-зависимости
FROM python-base AS runtime
RUN useradd --uid 10001 … app            # не root
COPY --from=builder /app/.venv /app/.venv
USER app
```

- **Две стадии.** uv и кеш сборки остаются в `builder`; в финальный образ
  попадает только готовое окружение `.venv` и код.
- **`--no-dev`.** pytest, Ruff, mypy и pytest-cov не устанавливаются. CI
  проверяет это: импорт `pytest`, `ruff`, `mypy` и команда `uv` в образе
  недоступны.
- **Digest, а не тег.** `python:3.12-slim` и `uv:0.12.23` закреплены по
  digest: тег можно переписать, digest — нет.
- **Сначала зависимости, потом код.** Изменение `app/` не переустанавливает
  библиотеки: слой с `.venv` берётся из кеша.

Размер образа — около 1 ГБ: scikit-learn, Pandas, PyArrow и Streamlit
тяжёлые. Сборка в CI — amd64; на Mac с Apple Silicon `docker compose up
--build` собирает arm64 локально.

## 5. Подготовка стенда без ручных шагов

`python -m app.bootstrap` выполняется при каждом `up` и безопасен при повторе:

1. **Схема.** Если версия Alembic в базе не последняя — выход с ошибкой,
   ничего не загружается.
2. **Данные.** Если таблица клиентов пуста — генерируется набор seed 42
   (20 000 заказов) и загружается одной транзакцией с проверками качества.
   Если данные уже есть — ничего не меняется. `DEMO_DATA=false` отключает
   загрузку.
3. **Токен интерфейса.** В томе `ui_token` хранится токен аналитика
   (файл с правами `0600`, владелец — пользователь `app`). Токен сохраняется,
   только если он действует и имеет роль `analyst`. Если в файле оказался
   `viewer`, он заменяется: иначе панель могла бы читать показатели,
   но вопрос агенту и сохранение отчёта возвращали бы `403`. Отозванный,
   просроченный, неизвестный или испорченный токен тоже заменяется.
   При выпуске нового токена прежние активные демо-токены интерфейса
   отзываются. Сам токен не печатается.

Запись файла также уточнена 22 октября 2026 года. `tempfile.mkstemp`
создаёт в том же каталоге новый файл с уникальным именем и правами `0600`.
После записи атомарная замена подставляет его на место `ui_token`:
читатель получает либо прежний файл, либо целый новый. Постоянное имя
`ui_token.tmp` не используется, поэтому оставшийся файл или символьная
ссылка с таким именем не перезаписываются. Если запись или замена завершились
ошибкой, новый временный файл удаляется.

У действующего analyst-токена обычный файл `0600` остаётся нетронутым.
Если права шире или вместо файла стоит символьная ссылка, bootstrap
записывает **тот же токен** в новый обычный файл `0600`. В JSON остаётся
`"ui_token": "kept"`: сохранился сам токен, хотя файл заменился.
Цель символьной ссылки не меняется; `chmod`, который мог бы пройти
по ссылке и изменить чужой файл, не вызывается.

```json
{"revision": "0004", "demo_data": "loaded", "rows": {"orders": 20000, …}, "ui_token": "issued"}
{"revision": "0004", "demo_data": "already present", "rows": null, "ui_token": "kept"}
```

Первая строка — первый запуск, вторая — после `down` и нового `up`.

Отдельно проверить выбор роли, права файла, старый `.tmp`, символьные
ссылки и очистку после ошибки можно без PostgreSQL:

```bash
uv run pytest -q tests/test_bootstrap_token_file.py
```

Проверка настроек — `uv run pytest -q tests/test_config.py tests/test_database_components.py`;
фактические результаты полного прогона фиксируются в
[VERIFICATION.md](VERIFICATION.md).

### Как интерфейс находит API внутри Docker

На машине интерфейс ходит на `http://127.0.0.1:8000`. В Docker API — это
другой контейнер с именем `api`, а настройки этапа 08 разрешали только
loopback-адреса: токен не должен уйти на чужой сервер. Решение:

- `UI_API_URL=http://api:8000` разрешён, только если `api` указан в
  `UI_ALLOWED_API_HOSTS`;
- в этот список можно записать только имя из одного слова (как имена
  сервисов Compose), но не домен вроде `example.com` и не IP-адрес;
- токен интерфейс читает из файла `UI_API_TOKEN_FILE`, смонтированного
  только для чтения.

## 6. CI/CD

```text
push / pull request / тег v1.2.3
 ├─ Lint, types and tests ─┐   Ruff, mypy, миграции, pytest + покрытие ≥ 90 %
 ├─ Audit runtime deps  ───┤   pip-audit по uv.lock, исключения со сроком
 │                         ▼
 └────────── Build and smoke test Docker
                 сборка → контракт образа → docker compose up → smoke
                 → down + up (данные и токен сохранились) → smoke
                           ▼  (только push)
            Publish tested image to GHCR
                 main → :main, :sha-<коммит>; v1.2.3 → :v1.2.3, :sha-<коммит>
```

| Задание | Что проверяет |
| --- | --- |
| `Lint, types and tests` | Как раньше, плюс покрытие строк и ветвей `app/` и `ui/` не ниже 90 % (сейчас 93.04 %) |
| `Audit runtime dependencies` | `uv export --no-dev` → pip-audit; находка вне списка исключений или просроченное исключение — ошибка |
| `Build and smoke test Docker` | Образ собирается из чистого контекста, работает не от root и без dev-инструментов; стенд поднимается командой пользователя; `scripts/smoke_stack.py` проверяет `/health`, `/ready`, 401 без токена, числа сентября, ответ агента с доказательствами, историю и здоровье интерфейса; после пересоздания контейнеров данные и токен на месте |
| `Publish tested image to GHCR` | Публикует **тот же** образ, что прошёл smoke, без пересборки; тег версии допускается только вида `v1.2.3` и только на коммите из `main` |

Права на запись пакетов есть только у задания публикации. Токен стенда
в журнале Actions маскируется и передаётся через переменную окружения.

## 7. Аудит зависимостей и политика 14 дней

С этапа 01 в lock попадают только выпуски старше двух недель
(`exclude-newer`): свежий пакет могли взломать, а за две недели это обычно
обнаруживают. Первый же аудит нашёл 25 известных уязвимостей:

| Пакет | Найдено | Исправлено в | Почему не обновили сразу |
| --- | --- | --- | --- |
| `pillow 12.3.0` | 24 CVE в разборе TIFF, GIF, PDF, EPS | `13.0.0` (16.10.2026) | Нужен ещё и Streamlit 1.66 (14.10); оба моложе 14 дней |
| `certifi 2026.7.22` | Недоверенный корневой сертификат emSign ECC Root CA G3 | `2026.10.19` (20.10.2026) | Моложе 14 дней |

Политика возраста и безопасность здесь столкнулись. Решение — явное
**временное исключение** в `scripts/audit-exceptions.json`:

- у каждой уязвимости есть причина, почему риск сейчас допустим.
  Наш код не декодирует, не загружает и не сохраняет изображения: Pillow
  приходит транзитивно через Streamlit. Единственный исходящий HTTPS — к
  OpenAI с фиксированным адресом;
- у каждой записи есть срок — 6 ноября 2026 года, не дальше 30 дней;
- аудит падает на новой уязвимости, на просроченном исключении и на
  исключении для уже исправленной уязвимости: принятый риск не забудется.

Обновление запланировано: Pillow 13 и Streamlit 1.66 — после 30 октября,
certifi — после 3 ноября. Порядок описан в
[DEPENDENCY_UPDATES.md](DEPENDENCY_UPDATES.md).

## 9. Ограничения

- Стенд локальный: HTTPS нет, порты только на `127.0.0.1`. Для сервера
  нужен обратный прокси с TLS и собственный пароль базы в `.env`.
- Пароль PostgreSQL по умолчанию — учебный: его хватает только для
  локального стенда.
- Лимиты частоты считаются в памяти одного процесса API.
- Публикуется образ amd64; arm64 собирается локально.
- Публикация в GHCR и зелёный CI этого этапа подтверждаются после push.
- Pillow и certifi обновятся только после двухнедельного «созревания»
  исправлений.

## 10. Проверь себя

1. Зачем двухстадийная сборка, если можно поставить всё в одном образе?
2. Почему базовые образы закреплены по digest?
3. Что произойдёт при повторном `docker compose up`, если данные уже есть?
4. Почему интерфейс не может обратиться к `http://api.example.com`?
5. Почему публикуется образ из smoke-проверки, а не собранный заново?
6. Почему уязвимость можно «принять», и что не даёт об этом забыть?

<details>
<summary>Ответы</summary>

1. uv, кеш сборки и dev-инструменты остаются в первой стадии: финальный
   образ меньше и не содержит лишнего для атаки.
2. Тег можно переписать на другое содержимое, digest — нет: сборка
   повторяема и защищена от подмены.
3. Bootstrap увидит клиентов в базе и ничего не загрузит; действующий
   analyst-токен интерфейса сохранится. Viewer будет заменён analyst,
   а небезопасные права или символьная ссылка исправятся заменой файла.
4. В список `UI_ALLOWED_API_HOSTS` можно записать только имя из одного
   слова; домены и IP-адреса отклоняются, а `UI_API_URL` проверяется по
   этому списку.
5. Новая сборка — новый образ, который никто не проверял. Публикуется
   ровно то, что прошло smoke.
6. Когда исправление ещё нельзя взять, а уязвимый код не достижим. Срок
   ≤ 30 дней и падение аудита на просроченном исключении не дают забыть.

</details>
